## 0. 预备知识：GPU 核是什么

讲算子前必须先建立 GPU 的执行模型——不然「分块」「融合」「寄存器」这些词都是空响。五分钟速成版：

### 0.1 硬件的层级

一块 GPU（以 H800 为例）从下往上是这样的：

```text
SM（Streaming Multiprocessor，流式多处理器）× 132 个
  ├─ 张量核（Tensor Core）：一次算一个 8×8×16 的小矩阵乘（FP8）
  ├─ CUDA 核：标量运算（地址计算、分支这些杂活）
  ├─ 寄存器：每 SM 256 KB，离 ALU 最近，纳秒级访问
  ├─ 共享内存（SRAM）：每 SM ~228 KB，同一 SM 内线程共享
  └─ L2 缓存：全卡共享 ~60 MB
HBM（显存）：141 GB，3.35 TB/s —— 大但相对"远"
```

**关键数字**：寄存器/SRAM 的访问速度比 HBM 快 1~2 个数量级，但容量小 3~4 个数量级。算子优化的全部艺术就是：**把数据搬运的层级上移（HBM→SRAM→寄存器），并把每次上移的「摊销次数」做大**。

### 0.2 软件的执行模型

CUDA 程序的最小单位是**线程**（thread），32 个线程捆成一个**warp**（ warp 是真正的调度单位——同 warp 的 32 个线程锁步执行同一条指令）。一个**核函数**（kernel，GPU 函数）启动时，成千上万个线程被组织成网格（grid）/线程块（block）铺到各个 SM 上。

一个形象比喻：GPU 是一支 132 个车间、每车间几十条流水线的工厂。你（kernel 的编写者）的任务是设计**分工表**（哪个线程算哪个输出元素）和**送料路线**（数据从哪级存储搬到哪级）。芯片的暴力（几千个张量核同时压数字）只有在分工表排得好、送料不堵的时候才能兑现——**算子工程 = 排产 + 物流**。

### 0.3 一个朴素矩阵乘的病

用伪代码写最朴素的矩阵乘（$\text{out}[m,n] = \sum_k A[m,k] \times B[k,n]$）：

```python
# ijk 顺序：外积视角的反面
for m in range(M):
    for n in range(N):
        acc = 0
        for k in range(K):
            acc += A[m, k] * B[k, n]   # B 按列访问——每次跨 K 个元素跳一次！
        out[m, n] = acc
```

每个输出元素要读 A 的一行（K 个）和 B 的一列（K 个）。B 按列访问在内存里是**跨步访问**（stride = N）——CPU/GPU 的缓存行（一次搬运的最小单位，64 字节）只用到 1/N，其余全浪费。总搬运量 $O(M \times N \times K)$ 个元素，而计算量也是 $O(M \times N \times K)$ 次乘加——**算术强度约 1 FLOP/byte，掉进最深的带宽陷阱**。

miniflow 的 `matmul_naive`（ijk）和 `matmul`（ikj）就是这个病的正面教材：仅仅交换两层循环（ikj 让 B 按行连续访问），CPU 上就能差一个量级——**不改数学、不改算法，只改访问顺序**。这就是算子工程的第一课。

### 0.4 分块：治病的通用药

上面的病根是「读进来的数据只被用一次就扔」。药方是**分块（tiling）**：把 A、B、C 都切成小块，比如 64×64 的 tile，一块 tile 装进 SRAM 后，让它的每个元素被用 64 次（和另一块的 64 列/行都乘一遍）：

```python
for i in range(0, M, 64):        # A 的行 tile
    for j in range(0, N, 64):    # B 的列 tile
        acc_tile = SRAM[64, 64]  # 累加器放 SRAM/寄存器
        for k in range(0, K, 64):
            a_tile = load A[i:i+64, k:k+64]      # HBM → SRAM
            b_tile = load B[k:k+64, j:j+64]      # HBM → SRAM
            acc_tile += a_tile @ b_tile          # 64×64×64 的小乘，全在 SRAM
        store C[i:i+64, j:j+64]
```

算一下摊销：每个 64×64 的 a_tile 从 HBM 搬进来（16 KB），参与 $64 \times 64 \times 64 = 26$ 万次乘加——**算术强度从 1 跳到约 64**（tile 越大越高，受 SRAM 容量限制）。深挖一层：张量核吃的是寄存器里的 8×8×16 片段，所以实际核是三层嵌套分块（tile→warp 级→张量核级），SRAM 的 tile 再切成寄存器碎片喂张量核——**分块是套娃的**，但思想只有一个：搬一次、用多次。

本章的所有算子都是这个思想的变奏。带着这个透镜往下读。

## 1. FlashMLA：为 MLA 注意力量身定制

### 1.1 先讲 MLA 解决什么问题

第 01 章说过，decode 的显存开销大头是 KV Cache。标准多头注意力（MHA）下，**每个 token、每一层都要为每个注意力头存一份 K 和 V**。以 128 头、每头 128 维计，一个 token 一层的 KV 是 $2 \times 128 \times 128 \times 2$ 字节（FP16）= 128 KB；61 层的模型，一个 token 的 KV 就是 $128\text{KB} \times 61 \approx 7.8$ MB，一条 4000 token 的请求要 31 GB——单卡 80 GB 显存放两条请求就满了，D 节点「KV 驻留密度」这个核心指标直接崩盘。

三代注意力结构都在治这个病，路线各有不同：

**MHA（标准）**：每个 Q 头配一个自己的 K 头和 V 头。$h$ 个头就是 $h$ 份 KV。表达力最强，KV 最贵。

**GQA（分组查询注意力）**：让若干个 Q 头**共享**一组 KV 头。比如 128 个 Q 头共享 8 个 KV 头（16:1），KV 直接砍到 1/16。代价是头间的多样性减少（同组的 16 个 Q 头看同一份 K/V）。Llama 系用它。压缩比可调，结构简单，是「性价比款」。

**MQA（多查询注意力）**：GQA 的极限——所有 Q 头共享 1 组 KV，压缩比 $h$ 倍。代价太狠，用的少。

**MLA（DeepSeek 的路线）**：不是「共享头」而是**换坐标系**——不存 K/V 本身，存一个它们的低维投影（latent）。数学上的巧妙让压缩比超过 GQA 的同时**不损失各头的表达能力**——这是它被评为「最优雅」的原因，也是代价：计算结构复杂了，通用算子跑不了，必须配 FlashMLA。

先看 MLA 的压缩数字，再讲它怎么做到的。

### 1.2 MLA 的数学：压缩与恢复

设隐藏维度 $d_{model} = 7168$（DeepSeek-V3），注意力头数 $n_h = 128$、每头维度 $d_h = 128$。

**MHA 的做法**：每个 token 的隐藏向量 $h \in \mathbb{R}^{7168}$，分别投影出 K 和 V：

$$
K = W_K h, \quad V = W_V h, \quad W_K, W_V \in \mathbb{R}^{7168 \times 16384}
$$

（16384 = 128 头 × 128 维）。K 和 V 各 16384 维——**存的是「展开后」的完整形态**。

**MLA 的做法**：先投影到一个极小的 latent 空间：

$$
c = W_{down} h, \quad W_{down} \in \mathbb{R}^{7168 \times 512}, \quad c \in \mathbb{R}^{512}
$$

缓存里只存 $c$（和另一个同样小位置的解耦 RoPE key，第 06 章展开这个细节）。需要 K/V 时用升维矩阵恢复：

$$
K = W_{up}^K c \in \mathbb{R}^{16384}, \quad V = W_{up}^V c \in \mathbb{R}^{16384}
$$

**KV Cache 的体积**：从 $2 \times 16384 = 32768$ 个数缩到 576 个数（512 latent + 64 解耦 key）——**约 57 倍压缩**。一条 4000 token 的请求，KV 从 31 GB 掉到约 0.55 GB。D 节点一张卡能驻留的请求数从 2 条涨到上百条——第 03 章「KV 驻留密度」从崩盘变成富裕。

一个自然的疑问：**为什么可以压这么狠？** 32768 维的 K/V 是从 7168 维的 $h$ 线性投影出来的——它们本来就活在一个至多 7168 维的子空间里，存 32768 个数本来就是冗余的。MLA 更进一步把投影拆成两段（7168→512→32768），相当于断言「有用的信息集中在 512 维的主子空间里」——这是训练出来的断言（$W_{down}/W_{up}$ 是可学的），对真实语言信息它成立。**有损压缩，但损失的是训练中被证明不重要的方向**。

### 1.3 吸收技巧：不恢复也能点积

压缩带来了新麻烦：注意力要算 $q^\top K$，K 是恢复出来的 $W_{up}^K c$。朴素路径是：每个历史 token 先升维恢复成 K（16384 维），再和 Q 点积——**计算量没省（还是全维度点积），中间还多了一步升维**，白忙。

关键技巧叫**吸收**（absorption）：注意到「恢复再点积」在数学上可以换序——

$$
q^\top (W_{up} \, c) = (q^\top W_{up}) \, c
$$

其中 $c$ 是 latent 向量，$W_{up}$ 是升维矩阵。与其给每个 token 恢复 K 再算点积，不如把 $W_{up}$ 预先乘进 Q 那侧——Q 是当前 token 现算的（每步只有 batch 数个），顺手就做了；而 $c$ 是每个历史 token 都要算的（几十万次），让它直接参与点积。变形之后：

- 每个历史 token 的点积从 16384 维降到 512 维（**32 倍计算量下降**）；
- **展开的 K/V 从未真正存在过**——升维矩阵被「吸收」进 Q，中间形态消失。

V 侧同理：$V \cdot (\text{输出投影})$ 的两个矩阵也能吸收合并。两头都吸收后，整个注意力的计算变成：**Q 侧预乘两个矩阵 → 与 latent 向量 $c$ 做低维点积 → 加权求和 latent → 一次性升维输出**。KV Cache 的体积和注意力的计算量同时下降，没有第三种代价——线性代数的结合律白送的午餐。

（这个变换 miniflow 有完整可跑的对照实现：`miniflow/attention.py` 里「朴素恢复路径 vs 吸收路径」两个函数，`tests/` 断言两者输出逐位一致——数学等价性不是背出来的，是测出来的。）

### 1.4 在线 softmax：不物化分 数矩阵

有了 MLA 的数据结构，剩下的问题是**怎么算得快**。先看注意力的原始公式：

$$
O = \text{softmax}(Q K^\top) \cdot V
$$

中间的 $S = QK^\top$ 是个 $L \times L$ 矩阵（$L$ = 序列长度）。朴素实现分四步：算 S（写显存）→ 读回 S 算 softmax（写显存）→ 读回 P 和 V 相乘（写显存）→ 输出。S 和 P 两个大矩阵各写一遍读一遍——$L = 8000$ 时，$S$ 有 6400 万个元素，FP16 下 128 MB × 来回数次。而**这些中间结果用完即弃**——为它们付搬运费纯纯冤枉。

Flash 系算子的核心思想是**根本不物化 S 和 P**。难点在 softmax 的分母：$\text{softmax}(s_i) = \frac{e^{s_i}}{\sum_j e^{s_j}}$——**要等整行分数都出来了才能归一化**，而「不物化」意味着分数是分块算的、算完一块就要腾寄存器。怎么办？

**在线 softmax**（online softmax）的分块重整化：把 K/V 切成小块逐块处理，每处理一块维护两个运行量——当前见过的最大分数 $m$ 和指数和 $l$。数学直接写出来：

维护运行状态 $(m, l, \text{acc})$（acc 是未归一化的加权和）。新来一块，算出块内分数 $s_{blk}$：

1. 块内最大：$m_{blk} = \max(s_{blk})$；
2. 更新全局最大：$m_{new} = \max(m, m_{blk})$；
3. **修正旧累积**：旧 acc 和 l 是按旧最大 $m$ 算的指数，现在最大值变了，指数的底数变了，全部乘上修正因子：

$$
l \leftarrow l \cdot e^{m - m_{new}} + \sum_{j \in blk} e^{s_j - m_{new}}, \quad \text{acc} \leftarrow \text{acc} \cdot e^{m - m_{new}} + \sum_{j \in blk} e^{s_j - m_{new}} v_j
$$

4. 最后输出 $O = \text{acc} / l$。

用一个 4 个数的小例子手算一遍（强烈建议拿笔跟着）：

```text
分数序列 s = [3, 1, 4, 2]，V = [10, 20, 30, 40]
分两块处理：[3,1] 和 [4,2]

第一块：
  m=3, l = e^0 + e^-2 ≈ 1.135
  acc = 1·10 + e^-2·20 ≈ 12.70（未归一化，按 m=3 平移）

第二块 [4,2]：
  m_blk = 4, m_new = max(3,4) = 4
  修正旧值：l ← 1.135 × e^(3-4) ≈ 0.417
            acc ← 12.70 × e^(3-4) ≈ 4.671
  累加本块：l ← 0.417 + e^0 + e^-2 ≈ 1.552
            acc ← 4.671 + 1·30 + e^-2·40 ≈ 40.21

输出：O = acc / l ≈ 40.21 / 1.552 ≈ 25.91

验证（一次性 softmax）：
  权重 = e^[3,1,4,2] / (e^3+e^1+e^4+e^2)
       ≈ [0.113, 0.015, 0.307, 0.041] （和≈0.476，实际是相对占比）
  O ≈ (0.238·10 + 0.032·20 + 0.645·30 + 0.086·40) ≈ 25.91 ✓
```

分块和一次性结果严格相等——**数学上等价，工程上中间结果全部待在寄存器/共享内存里，显存占用从 $O(L^2)$ 降到 $O(L)$，S/P 矩阵每个元素只在寄存器里存在一瞬**。这个算法是 FlashAttention（2022）奠基的，FlashMLA 把它适配到 MLA 的 latent 结构上——点积的维度是 512（latent）而不是 128（每头），分块形状、寄存器分配全部重排。

（这个例子 miniflow 里也有对应的实验：`tests/` 里在线 softmax vs 朴素 softmax 的逐位一致性断言 + 一个手算例子的小测试。改一行「分块大小」看结果不变——**分块尺寸不影响数学，只影响性能**，这是分块算法的美德。）

### 1.5 FlashMLA 的 decode 专用布局

在线 softmax解决的是「不物化中间矩阵」；FlashMLA 还有第二个要害——**为 decode 的形状特化内存布局**。

decode 时每条请求只有 1 个新 token，但批内可能有 200 条请求——形状是「序列维度极小（1）、请求维度极大（200）、latent 维 512」。通用注意力核按「头 × 序列」组织分块，在这个形状下访存全是一个 token 一个 token 的碎读（每请求每头独立一小段 KV）。FlashMLA 按「请求 × latent 维」排布分块：把批内 200 条请求的 latent KV 排成**一个连续大矩阵**（200 × 512 每头），一次大段读——正好治第 01 章诊断的「decode 喂不饱芯片」。

数字感受：碎读 200 次 × 每次几十 KB（延迟主导，每次 ~2 μs）≈ 400 μs；连续读 10 MB 一段（带宽主导，3.35 TB/s）≈ 3 μs。**两个数量级的差距纯粹来自「数据怎么摆」**。这也是「模型结构和引擎算子互相成就」（第 01 章 5 节）的具体机制：MLA 的 latent 结构天然把 200 条请求的 KV 变成同构矩阵块（都是 512 维），FlashMLA 才有连续布局可排——GQA/MQA 各头 KV 长度不一，排不出这么整齐的矩阵。

!!! note "MHA → GQA → MLA 的递进"

    三代结构都在压 KV Cache：MHA 每个头独立存 KV；GQA 让若干个 Q 头共享一组 KV 头（头数维度直接砍）；MLA 更进一步，所有头共享一个 latent 向量，靠吸收技巧恢复各头差异。miniflow 用 GQA 复刻「KV 头数 < Q 头数」的结构收益（`miniflow/config.py`：`num_kv_heads=2 < num_attention_heads=4`）——数学复杂度换成可读性，是教学取舍。

### 1.6 FlashMLA 的性能画像

公开 benchmark 的量级（H800，decode 形状）：

- **带宽利用率**：约 3000 GB/s 以上（对照峰值 3.35 TB/s，**九成以上**）——带宽受限负载的满分卷面；
- **对比未优化的 MLA 参考实现**：数倍提升——差距主要来自布局（碎读变连续读）和分块流水。

一个值得体会的视角：FlashMLA 的「快」**不是算得快**——算术强度 2 的负载里 ALU 本来就闲着——而是**搬运效率高**。九成带宽利用率意味着：每字节的 HBM 流量都对应着有效计算，没有碎读的浪费、没有中间矩阵的往返、没有布局错位的空转。**带宽受限算子的满分标准是「带宽利用率」，正如算力受限算子的满分标准是 MFU**——两把尺子，量两种负载。

### 1.7 MLA 的历史坐标：注意力结构进化的第三条路

把 MLA 放进注意力结构的历史里，能看到一个有趣的方向之争——**三条路线都在治 KV 爆炸，药理完全不同**：

**路线一：减 KV（GQA/MQA）**。直接砍存储——共享头。这是「工程妥协」路线：接受表达力损失换显存。Llama 2/3、多数开源模型的选择。优点是结构简单（对算子友好，现成 kernel 改改就能跑），缺点是压缩比有限（16:1 附近就伤质量了）。

**路线二：换算法（线性注意力/滑窗）**。把 $O(L^2)$ 的注意力本身换成 $O(L)$ 的递推形式（状态空间模型 Mamba 是这条路的旗手）。数学上更激进——复杂度直接降维打击。代价是「模拟全量注意力」的能力有理论上限，长程精确检索类任务会露馅（ Needle-in-a-haystack 类评测）。

**路线三：换表示（MLA）**。注意力机制原封不动，只换 KV 的**存储表示**——低维 latent + 恢复矩阵。「数学等价性」是它的护城河：训练时按完整 MLA 算、推理时用吸收形式算，两者逐位等价——**没有任何精度妥协的压缩**。这是它和「KV 量化」（另一个压缩手段，有损）的本质区别。

为什么 DeepSeek 选路线三？一层背景：**路线三需要「模型团队和算子团队坐在一起」**——MLA 的 latent 结构必须配 FlashMLA 的专用核（通用库跑 GQA 是现成的，跑 MLA 原始形态反而慢——恢复矩阵的朴素乘法比 GQA 还贵）。有自研算子能力的模型公司才有资格选这条路。**结构创新深度绑定工程能力，这就是 DeepInfer 存在的意义**（第 01 章 5 节的论点在这里落地成最硬的案例）。

路线之争没有终局：GQA 的简单仍是多数模型的选择，线性注意力在长序列场景继续进化，MLA 证明了「第三条路」可行后也被后来者借鉴（各种 latent 变体）。**学结构的要点不是背结论，而是掌握三条药理——下次见到任何新注意力论文，先问它走哪条路、付出什么代价**。

（一个预告：MLA 有个「不优雅但必要」的补丁——解耦的 RoPE key。位置编码的旋转操作和「吸收」数学上冲突，DeepSeek 的解法是单独存一份小位置 key 不参与吸收。这个细节第 06 章算 KV 字节时精确展开——现在只需知道「latent 576 维 ≈ 512 + 64 的构成」。）

## 2. DeepGEMM：两种模式对应两种负载

### 2.1 GEMM：前向计算的骨架

矩阵乘（GEMM，GEneral Matrix-Matrix multiply）占整个前向计算的绝大部分——除注意力外的所有投影（Q/K/V/O、MoE 的门控/专家、共享层）全是 GEMM。第 01 章「推理 = 依次读取一大堆矩阵 + 做乘加」的画面里，「做乘加」就是 GEMM。

GEMM 的标准形状 $\text{out}(M \times N) = A(M \times K) \times B(K \times N)$：

- **M**：行数。prefill 时是 token 数（几千），decode 时是 batch × 1（几十到几百）——**两个世界的分界线就在这一维**；
- **N**：输出特征维（权重的输出维度，7168 或专家的中间维 2048）；
- **K**：求和维（权重的输入维度）。

B 是权重（推理中不变，常驻显存），A 是激活。GEMM 的算术强度 $\approx \frac{2MNK}{2(MK + KN + MN)}$，当 M、N、K 都是几千时高达上千 FLOPs/byte（算力受限）；当 M=1 时塌缩到约 1（带宽受限）——**同一个算子，M 维的变化把它从屋顶右侧扔到左侧**（Roofline 语境）。

### 2.2 FP8：精度换带宽的通行证

DeepGEMM 的全称是「FP8 GEMM」——它只在 FP8 精度上做到极致。FP8 细节值得两段：

**格式**：FP8 有两种变体（E4M3：4 位指数 3 位尾数，动态范围大、精度低，用于前向权重/激活；E5M2：范围更大精度更低，用于梯度）。对比 FP16（E5M10）：尾数从 10 位砍到 3 位——**数字的「分辨率」从 1/1024 粗化到 1/8**。

**缩放因子（per-block scaling）**：直接把 FP16 数值转成 FP8 会大量溢出/下溢（动态范围不够）。解法是分块缩放：把矩阵切成 128×128 的块，每块记一个缩放因子（FP32），块内数值除以它再转 FP8——**每块的数值范围独立适配**，精度损失压缩到接近无损。代价是 GEMM 核要「带着缩放因子算」（每块乘完再乘 scale），核内多了几个乘法——这是 FP8 GEMM 和普通 INT8 GEMM 的主要区别，也是「为 LLM 重新发明 FP8 GEMM」的原因（通用 INT8 库没有这种 per-block scale 语义）。

**收益**：权重和激活的搬运量减半（1 byte/数），张量核的 FP8 吞吐是 FP16 的两倍——带宽受限侧收益直接（搬运减半），算力受限侧收益翻倍（吞吐翻倍）。**两边都赚，代价是精心设计的缩放**——这笔交易 DeepGEMM 做到了工业级可靠。

### 2.3 满血模式（prefill 侧）：经典极致

prefill 的 GEMM 形状天然肥硕：几百条请求 × 各几千 token 的 M 维（上万），乘上 N=7168、K=7168 的权重。这种形状用大 tile 分块（如 128×256）+ **异步流水线**把算力打满。

「异步流水线」的关键硬件是 **TMA**（Tensor Memory Accelerator，张量搬运加速器——Hopper 架构引入的独立搬运单元）：它是一个专职 DMA 引擎，可以「设定好后自己搬、搬完通知我」。核的执行变成双缓冲轮舞：

```text
时间 →
计算： [ tile#1 计算          ][ tile#2 计算          ][ tile#3 ...
搬运（TMA）：   [ tile#2 装载 ][ tile#3 装载 ][ ...
              ↑ 计算和搬运重叠：算 tile#1 时，TMA 在搬 tile#2
```

没有 TMA 的旧时代，搬数据要占着线程（同步拷贝）——算和搬串行，每步都有一段「光搬不算」的空窗。TMA 让两者并行，**空窗消失，MFU 上探 60%+**（对照第 02 章的 MFU 损耗清单，「通信/搬运空洞」一项的歼灭武器）。

### 2.4 连续布局模式（decode 侧）：拼小为大

**decode 侧才是巧劲。** decode 时单条请求的 GEMM M=1——一个 token 乘权重矩阵，怎么摆都是「瘦条」（1×7168 乘 7168×7168）。张量核的 tile 是 8×16 起，M=1 意味着 tile 的行方向空 7/8——**算力利用率掉到 2% 量级**。而 decode 是带宽受限，这个「算力浪费」看起来无害（ALU 反正闲着）？

有害。因为 M=1 的 GEMM 读完整权重只服务 1 个 token——回到第 01 章的原始账：37 GB 搬运只做 74 GFLOPs。**组批已经在引擎层把这个账改善到 1/64（batch 摊销）**，但 MoE 层有额外的麻烦：每条请求路由到的专家不同，「每个专家分到的 token 数」参差——200 条请求 × 8 专家 = 1600 个 (请求,专家) 对，散落在 256 个专家上，平均每专家 6 个 token，**每个专家的 GEMM 是 M=6**——比 M=1 略好，但仍是瘦条。

DeepGEMM 的 decode 模式把所有这些对的输入行**拼接成一段连续内存**（按专家分组排布），对每个专家形成 M=若干的「胖条」GEMM；同时因为拼接是连续布局，装载权重的读取也是大段连续。这不是简单的 concat 技巧：

- 路由器输出的「token → 专家」映射要即时转成「按专家分组排序的连续内存」（一次分段排序/计数）；
- dispatch（DeepEP 的通信）要按这个分组直接把 token 发到专家所在卡的正确偏移位置——**通信的接收缓冲区就是 GEMM 的输入矩阵**，零拷贝衔接；
- GEMM 核要支持「M 维由运行时决定、每组独立 scale」的分组模式。

**路由、通信、算子的内存布局从头设计成一体**——这正是 DeepGEMM 必须和 DeepEP 配对出现的原因（下一节），也是「DeepInfer 的算子不是库而是系统」（第 01 章 5 节）的最硬核证据。

一个数字感受两模式的差距：M=6 的分组 GEMM 在 H800 上可能只跑到峰值的 2%；拼成连续布局的 M=1600（理想路由均匀时），能到 60% 以上。**P/D 分离在算子层的投影就是这两套 GEMM**——反过来说，两类负载的算子形状差异大到值得物理分离，架构不是拍脑袋拍的。

### 2.5 一个 GEMM 的完整账：从形状到时间

把两模式的账合起来算一遍，建立「看到形状就能估时间」的手感（这是算子工程师的基本功，也是你评估任何「新硬件/新模型」的速算工具）。

**满血模式的一步**：prefill batch 里 3 条请求各 4000 token（拼成 M=12000），某投影层 N=K=7168，FP8：

```text
计算量 = 2 × M × N × K = 2 × 12000 × 7168 × 7168 ≈ 1.23 TFLOPs
满血模式 MFU 60% → 有效算力 600 TFLOPS
耗时 ≈ 1230 / 600 ≈ 2.05 ms
搬运 = 权重 7168×7168×1B ≈ 51 MB + 激活 12000×7168×1B ≈ 86 MB ≈ 137 MB
带宽时间 = 137 MB / 3.35 TB/s ≈ 0.04 ms ≪ 计算时间 ✓（算力受限的验证）
```

**连续布局模式的一步**：decode batch 200 条请求过同一个投影层（M=200，N=K=7168）：

```text
计算量 = 2 × 200 × 7168 × 7168 ≈ 20.5 GFLOPs
但 M=200 的 tile 排不满 —— 若只用满血模式，MFU 约 5%，耗时 ≈ 0.4 ms
连续布局 + decode 优化核：MFU 拉到 ~40%，耗时 ≈ 0.05 ms
搬运 = 权重 51 MB（主导）+ 激活 1.4 MB
带宽时间 = 52 MB / 3.35 TB/s ≈ 0.016 ms
≈ 计算时间 —— 两头都接近极限 ✓（decode 是"骑在屋脊上"的负载）
```

第二笔账里注意两个点：一是 **MFU 40% 在 decode 是好成绩**（不是 60%——M 小的天然约束），二是计算时间和带宽时间几乎相等——decode 的 GEMM 已经骑在 Roofline 屋脊的转折点上，**任何一边的优化都会立刻被另一边卡住**。这就是 decode 优化的狭窄感：算子和带宽必须一起抠，差一边就白干。

**把账外推**：61 层 × 若干投影/专家层，每 step 的 GEMM 总量就出来了——乘上第 03 章的 step 预算（SLO ITL 100 ms 里 decode 计算只占一部分），能反推「这个集群最多跑多大 batch」。**看到形状估时间 → 估 batch → 估容量，这条速算链是架构沟通的通用货币**（评估新模型的第一封邮件通常就是一张这样的表格）。

### 2.6 从满血到连续布局：一个统一的视角

两套模式不是两个孤立的核，而是同一个优化函数在两个工作点上的解。GEMM 的性能模型（简化）：

```text
耗时 T ≈ max( 计算时间 2MNK / (MFU × 峰值算力),
              搬运时间 2(MK+KN+MN) / 带宽 )

M 大 → 计算项主导 → 优化 MFU（大 tile、深流水）     = 满血模式
M 小 → 两项接近   → 同时抠两头（拼 M、省搬运）       = 连续布局模式
```

`max` 里两项的相对大小决定优化方向——**Roofline 不只是分析框架，是设计决策树**。DeepGEMM 把两个分支都做到了工程极致，而分界线（M 多大算「大」）由硬件参数定：$M^* \approx$ 带宽 × K / (MFU × 峰值算力) 量级——每代硬件换代，分界线移动，两个模式的适用范围跟着挪。**硬件代际迁移时最先重估的就是这些分界线**（H800 → B200 算力涨快于带宽，分界线上移，满血模式的甜点区扩大——decode 侧的连续布局反而更重要了）。

## 3. DeepEP：MoE 的瓶颈是通信

### 3.7 预备：GPU 集群的通信底座

讲 DeepEP 的三板斧前，值得花一页建立通信底座的词汇——不然「NVLink/RDMA/协议栈」都是名词轰炸。

**两级互连**。GPU 集群的网络分两级：

- **节点内（8 卡之间）**：NVLink——GPU 之间的专用高速总线，带宽 ~900 GB/s（第四代），延迟亚微秒。它不走以太网协议、不经过 CPU，是「八张卡背靠背焊接」的直连；
- **节点间**：RDMA（Remote DMA）网络——通过网卡（如 InfiniBand/RoCE）直接读写远端机器的内存。带宽 ~400 GB/s（较 NVLink 低一档），延迟微秒级。

MoE 的 all-to-all 要同时跨两级：同节点 8 卡走 NVLink、跨节点走 RDMA——**DeepEP 的拓扑感知路由就是在调度「哪些流量走哪条路」**。

**软件路径的三个时代**。通信的「固定开销」来自软件路径，它有三个层次：

```text
时代一（内核态 verbs）：应用 → 系统调用 → 内核驱动 → 网卡
    一次 send ~几十微秒（上下文切换 + 协议处理）
时代二（用户态 verbs）：应用 → 用户态驱动 → 网卡
    ~10 μs 级（免上下文切换，但仍有库调用开销）
时代三（轮询直达）：应用直接轮询网卡完成队列
    ~2 μs 级（没有"调用"，只有"看一眼"）
```

DeepEP 低延迟内核住在时代三——**「消灭仪式」的具象化就是这条路径的缩短**。代价是轮询烧 CPU 核（要专门留核盯网卡）——工程的世界没有免费午餐，只有换来的午餐。

**NCCL 是什么**：NVIDIA 的集合通信库（GPU 通信的「标准库」），实现了 all-reduce/all-to-all 等集体操作的成熟优化。为什么不直接用 NCCL？因为 NCCL 的设计目标是「大消息吞吐」（训练的梯度同步场景：几百 MB 的消息），它的软件路径对 decode 的几十 KB 小消息是杀鸡用牛刀——固定开销吃不消。DeepEP 等于「为小消息重写了 NCCL 的 decode 子集」——**通用库的甜点区之外，就是自研算子的生存空间**。

### 3.8 MoE 前向的完整解剖

DeepSeek 的 MoE 层每前向一步要做三件事：

```text
dispatch：  每张卡把自己负责的 token 按路由表发往「专家所在的卡」  （all-to-all）
compute：   各卡上的专家对自己的 token 做矩阵乘
combine：   算完的结果发回原卡，按路由权重加权求和              （all-to-all）
```

注意一个容易看漏的事实：**计算本身不重**（MoE 每 token 只激活 37B/671B 的参数，且都是 M 已拼大的 GEMM）——**瓶颈在两次 all-to-all 通信**。

all-to-all（全交换）是什么：每张卡都要给其他每张卡发一份不同的数据。64 卡的集群，dispatch 阶段每卡发 63 份消息、收 63 份。这个模式比 broadcast（所有人收同一份）和 reduce（汇总到一处）都「碎」——**它是「点对点 × N²」的组合**，对网络的利用率最难做满。

### 3.2 两头受气：prefill 拼带宽，decode 拼延迟

通信的两个性能维度——**带宽**（数据流多快）和**延迟**（一次往返的固定时间）——在 MoE 的两侧各占一头：

**prefill 侧**：token 多，通信量 = token 数 × top-k 路由 × hidden 维度。10000 token × 8 专家 × 7168 维 × 1 字节（FP8）= 573 MB 每层每卡群——数据量大，传输时间由带宽决定（几百 GB / 3.35 TB/s ≈ 毫秒级）。**拼的是带宽**：NVLink（卡间，~900 GB/s）和 RDMA（跨节点，~400 GB/s）都要跑满。

**decode 侧**：每卡每步只发一两个 token（batch 64 ÷ 64 卡），消息几十 KB——**传输本身只要微秒级，但网络的固定开销（协议栈、握手、软件路径）是几十微秒**。数据传输时间成了零头，固定开销反客为主。**拼的是延迟**：谁砍掉固定开销谁赢。

两个不同的病，一副药没用——所以 DeepEP 装了两副牙齿。

### 3.3 板斧一：双模式内核

**prefill 的高吞吐模式**：常规 all-toall 的优化版——NVLink/RDMA 混合拓扑感知路由（同节点走 NVLink、跨节点走 RDMA）、大消息合并、带宽打满。这副牙齿是「标准身材」：数据大、时间由带宽定，把带宽利用率做到极致就完事。

**decode 的低延迟模式**是真正的黑科技。它躲开的三层固定开销：

1. **协议栈**：常规 RDMA 走 verbs 接口 → 内核驱动 → 网卡，路径上百万指令。低延迟模式用 **RDMA 直达**（用户态轮询，网卡和用户内存零交互）——路径砍到万级指令；
2. **同步语义**：常规 collective 要「全员到齐」才开始（每卡等最慢的）——64 卡里有一台抖了 10 μs，全体陪等。低延迟模式用**钩子式推进**：数据一到位立刻通知计算开始，不等全员；
3. **拷贝次数**：常规路径 dispatch 收到 → 拷到中间缓冲 → 再拷到计算布局。低延迟模式让**接收缓冲区直接就是 GEMM 输入布局**（和 DeepGEMM 连续布局模式的呼应）——零拷贝。

三层开销砍完，一次 dispatch 的固定开销从几十微秒压到几微秒——decode 每步 10~50 ms 的预算里，通信从「显著占比」变成「几乎看不见」。**低延迟通信的设计哲学：消灭的不是传输时间，是「等待和搬运的仪式」**。

### 3.4 板斧二：FP8 传输

dispatch 的 token 以 FP8 传输，通信字节数直接减半。

为什么敢：通信传输的是中间激活值（hidden 状态），不是最终输出——FP8 的精度损失发生在「进专家前」的表示上，专家矩阵乘的输出再聚合回来，误差被稀释在多层传播里，**最终输出的差异几乎不可测**（DeepSeek 的技术报告有端到端评测背书）。

为什么值：通信量减半在 prefill 侧直接省一半带宽时间；在 decode 侧虽是延迟主导（字节减半用处小），但小消息的序列化时间（把数据塞进网络的固定成本）也减半——两头都赚。**用一点数值精度换一倍通信效率**，和 GEMM 的 FP8 是同一个哲学的两次落地。

### 3.5 板斧三：通信-计算重叠

第三板斧治「干等」：dispatch 完整结束前，先到的 token 不能算吗？

DeepEP 的 dispatch 按「先到先算」钩子式推进——哪批 token 先到位就先算哪个专家，通信的尾巴（最慢的那几张卡的 token 还在路上）被先到的计算盖住。combine 同理：算完的专家先发回，聚合在收到第一批时就开始（在线式的加权求和，和在线 softmax 是同构的技巧——**分块处理 + 运行状态，一口气吃掉「等全量」的串行依赖**）。

极限情况下通信时间被计算时间完全覆盖（计算 ≥ 通信时），MoE 层的墙钟时间 ≈ 纯计算时间——**通信「消失」了**。这是所有并行系统的终极追求：让不可消除的通信变成不可见的通信。

### 3.6 三板斧的合力：一次 decode step 的时间线

把三板斧合起来，看一个 64 卡 decode step 里 MoE 层的完整时间线（量级示意）：

```text
t=0     dispatch 发起（64 卡各发 ~50 KB 的路由消息）
t=3μs   第一批 token 到位（低延迟内核，零拷贝直入计算布局）
t=3μs   首批专家开始计算（钩子式推进，不等全员）
t=10μs  全部 token 到位（通信尾部，已被计算覆盖）
t=50μs  各专家 GEMM 完成（M 拼大的连续布局 GEMM）
t=53μs  combine 首批发回，聚合开始（在线式加权求和）
t=70μs  MoE 层完成 —— 通信显性时间 ≈ 0（全被重叠）

对照（无优化）：dispatch 40μs（协议栈+同步等待）
              + 计算 60μs（M 碎的 GEMM）
              + combine 35μs（等全员+拷贝）
              ≈ 135μs，通信占 55%
```

一个 MoE 层 135→70 μs，61 层的模型每 step 省 4 ms——对 TPOT 50 ms 的预算是 8% 的直接改善。**算子层的「几个百分点」加起来就是第 02 章成本链上的真金白银**。

## 4. TileLang：手写与生成的分界线

### 4.1 为什么需要 DSL

FlashMLA 和 DeepEP 这类核是手写的（CUDA、甚至汇编级微调），一个核的工程成本以人月计。而模型结构在快速迭代——每个新结构（新的注意力变体、新的专家结构、新的融合模式）都想要匹配的核。全手写跟不上节奏，全靠通用编译（Triton 之类）又拿不到极致性能（通用抽象必须照顾所有模式，牺牲特定结构的排布自由度）。

TileLang 是 DeepSeek 的算子 DSL（领域专用语言）：你用「分块 + 循环 + stage」的抽象描述算法结构（比如「K/V 切 64 列一块，循环内累加，寄存器里维护 running max」），编译器负责「排产 + 物流」的细节（线程怎么分、共享内存怎么排、TMA 怎么编程、流水线怎么重叠）。**人类出算法结构，机器出执行细节**——两头都是各自擅长的。

一个 TileLang 内核和对应 CUDA 的对比（示意）：描述行数从几百行降到几十行，性能达到手写的 90%+（部分算子反超——编译器排的流水线偶尔比人手更耐烦）。FlashMLA 本身的部分变体就是用 TileLang 写的（仓库里有对照实现）——**吃自己的狗粮，且狗粮真香**。

### 4.2 分界线

- **通用热核**（MLA、GEMM、EP 通信）：手写，榨干每一滴带宽——这些核每天跑亿万次，1% 就是巨额；
- **长尾与新结构核**（新算子原型、融合变体）：TileLang 写，快速验证性能上限，跑赢了再考虑要不要手工精修。

这套「手写保底 + DSL 提效」的组合，是算子团队能跟上模型结构快速迭代的方法论——第 01 章说「每一代模型的变化兑现成新算子」，TileLang 就是兑现的流水线。

（对 DSL 感兴趣的读者：TileLang 的抽象「tile + pipelined loop + multi-stage buffer」恰好是本章 0.4 节分块套娃的形式化——你用它的语法写一遍朴素 GEMM，就明白 0.4 节的三层嵌套为什么长那样。）

## 4.5 算子工程师的一天：这个团队怎么工作

把四个组件拼成团队视角，看看「算子层」作为组织怎么运转——这能回答「学这章有什么用」之外的问题：**这些人是怎么协作的**。

**输入是什么**：模型团队给一个新结构（比如 V3 的 MLA 或下一代的新变体），附带参考实现（PyTorch 慢版）和精度基准。**输出是什么**：生产级核——比参考快 5~50 倍、精度对齐（端到端评测不掉点）、带完整测试矩阵（各种形状/批量/边界）。

中间的典型流程（以 FlashMLA 的传说为原型）：

```text
1. 性能剖析：参考实现跑一遍，nsight/ncu 工具看时间花哪
   （结论通常是：xx% 在 HBM 搬运、yy% 在等待——第 01 章的诊断重演）
2. 算法重构：找数学等价变形（吸收、在线 softmax、分块）
   ——这一步是"研究"，纸上推导 + 小实验验证等价性
3. 布局设计：数据在 SRAM/寄存器怎么排（decode 专用布局的来源）
4. 流水编排：TMA/计算/同步的三方调度（双缓冲轮舞）
5. 调优扫参：tile 尺寸、流水深度、占用率——参数空间网格搜索
   （自动化调参 + 人工洞察，往往最后 10% 靠人）
6. 精度回归：和参考实现逐位/逐块对比 + 端到端评测
```

每一步的工具链（profiler、TileLang、CI 的形状矩阵测试）都是基建投资。**DeepInfer 算子团队的效率不是个人英雄，是流水线**——TileLang 那节说的「手写保底 + DSL 提效」是流水线的两条传送带。

一个反直觉的观察：**算子工程师最大的时间投入往往不是「写快」而是「证明没写错」**。数学等价性的验证（各种形状的逐位断言）、精度回归（端到端不掉点）、边界条件（极端长度、空 batch、单 token）——测试矩阵的行数经常超过核本身的代码。原因很简单：算子 bug 的爆炸半径是「全集群所有输出错乱」，而它藏在一堆位级操作里极难排查——**质量投资的密度和故障半径成正比**，这是本章工程课的隐藏主线。

## 5. miniflow 的算子层

miniflow 用一个三层结构把「算子层值得单独一章」这件事复刻出来：

```text
miniflow/tensor.py     NumPy 参考实现（清晰、可单测、行为基准）
csrc/kernel.cpp        C++ 后端（pybind11 编译为 miniflow._C）
                        ↳ BACKEND 探测：编译成功则派发 C++，否则回落 NumPy
```

三个教学点直接写在代码里：

1. **`matmul_naive` vs `matmul`**：同样的 $O(M \cdot K \cdot N)$，`ijk`（内积视角）与 `ikj`（外积视角）两种循环序在 CPU 上差一个量级——**循环序决定缓存局部性**。DeepGEMM 的分块是同一思想的 GPU 极致版：让每个数据块在被缓存期间被用尽可能多次；
2. **`fused_silu_swiglu`**：SwiGLU 的 `silu(gate) * up` 原本是三个算子（两次逐元素算子加一次乘法），中间张量要在内存里写读两遍；融合成一个核后一遍过——decode 访存受限，**省一次搬运就是纯赚**。这也是 GPU 算子融合（把一串小 kernel 合成一个大 kernel，消掉 kernel 启动开销和中间落显存）的最小教学标本；
3. **`softmax` / `rms_norm`**：数值稳定的标准实现（减 max 再指数化）。FlashMLA 的在线 softmax 是它的分块推广——`tests/` 里可以验证两者数学等价。

```bash
pip install pybind11 && python setup.py build_ext --inplace
python -c "from miniflow.tensor import backend; print(backend())"
# 编译成功输出 cpp，否则 numpy —— 功能完全等价，只是性能不同
```

!!! warning "一个诚实的提醒"

    miniflow 的 C++ 核在 CPU 上**未必比 NumPy 快**——NumPy 底层是工业级 BLAS。这里的数值在于看清「同一数学的三种实现，工程差距从哪来」（循环序、融合、布局），不在跑分。GPU 上的 FlashMLA/DeepGEMM 与 CPU 上的 naive 实现，差距来源是同一组思想，只是幅度不同。

### 5.4 miniflow 算子层的第四个教学点：BACKEND 探测

`BACKEND` 探测这个设计本身值得单独说——它复刻的是**生产框架的「能力探测 + 优雅回落」**模式：

```python
try:
    from miniflow import _C          # C++ 扩展编译过
    BACKEND = "cpp"
except ImportError:
    BACKEND = "numpy"                # 没编译 → 回落，功能不损
```

DeepInfer 的引擎启动时同样探测环境：FlashMLA 的 CUDA arch 支持？DeepEP 的 IB 网卡在吗？3FS 客户端挂载权限？——**任何一项缺失都回落到慢但正确的路径**（CPU 参考实现 / NCCL 通信 / 本地缓存）。生产系统不能假设部署环境完美，「同一行为的多级实现」是韧性的来源。

对教学项目还有第二层意义：**测试矩阵可以分别在两个 backend 上跑同一套断言**——C++ 核和 NumPy 参考逐位一致，是「重构没改语义」的最强证明（和 FlashMLA 论文里「核 vs 参考实现的对拍」同构）。你在 `tests/` 里看到的 backend 参数化测试就是干这个的。**写高性能代码的工作流：先写对的，再写快的，用前者给后者当裁判**——这个工作流比任何单个算子的技巧更值得带走。

## 6. 三大算子的共同哲学：把「摊」做到底

把镜头拉远，本章四个组件其实是同一个公式的四次代入。**算子层的一切优化都在最大化「每次搬运的摊销」**：

| 组件 | 摊什么 | 怎么摊 |
|---|---|---|
| 分块 GEMM（0.4 节） | 一次 HBM 装载 | tile 进 SRAM 后被用 tile 次数遍 |
| FlashMLA 布局 | 一次连续读 | 200 条请求的 latent 拼成大矩阵 |
| 在线 softmax | 寄存器驻留 | 分块累加，中间矩阵不落显存 |
| DeepGEMM 连续布局 | 一次权重读 | 1600 个 (token,专家) 对拼成大 M |
| DeepEP 零拷贝 | 一次通信 | 接收缓冲区直接是计算布局 |
| 通信-计算重叠 | 通信时间 | 被先到的计算覆盖（时间维度的摊销） |

「摊」的反面是「浪费」：碎读浪费带宽（利用率不满）、物化中间结果浪费搬运（来回两趟）、同步等待浪费时间（全员陪等最慢者）。**算子工程师的职业病就是看见任何「搬了只用一次」「等了不干活」的代码就难受**——这个职业病值得你也染上，写任何性能敏感的代码都用得上。

摊销的数学本质值得最后点一次：**摊销 = 共享**。tile 内的 64 次乘加共享一次装载；200 条请求共享一段连续读；1600 个对共享一份权重流；先到的计算共享通信的等待时间。第 02 章确定性一节说过「效率来自共享、确定性要求隔离」的张力——在算子层，没有确定性的约束（请求内部的计算随便共享），所以摊销可以做到物理极限。**这就是算子层性能上限远高于引擎层的结构性原因**：它工作在「单请求内部」，那里没有跨请求的隔离税。

### 一个反例教学：什么时候「摊」不动

为了防止「分块万能」的错觉，看一个摊不动的场景：**batch=1 的 decode 注意力**。

一条请求、1 个新 token、历史 10 万 token 的 KV。FlashMLA 再怎么分块，这 10 万 token 的 latent（约 57 MB）每个字节都必须读一遍——它们只和这 1 个 Q 点积，**没有别人可以共享**。带宽时间 57 MB / 3.35 TB/s ≈ 17 ms，一步就 17 ms——超长上下文单聊的物理极限，任何算子都救不了。

解法只能来自「摊销对象」的扩展：多开几条并发（引擎层的组批）、或让历史 KV 更小（模型层的 MLA 已经做了 57 倍、再压就是量化）。**算子的「摊」有边界：数据的共享结构有多丰富，摊销就有多大空间**——这个边界反过来定义了引擎层（组批造共享）和模型层（结构造压缩）的存在意义。三层各自摊各自的，合起来才是完整的答案。

## 7. 常见误解澄清

**误解一：「算子优化是玄学拼手速。」** 高性能核的设计空间虽大，但主线思想本章已经给全：分块摊销、融合少搬、布局连续、流水重叠、精度换带宽。所谓「手写 vs 编译」的差距，是这些思想的应用深度差（TMA 流水的层数、寄存器分配的精细度），不是无迹可寻的玄学。**先建立心智模型，再看 CUDA 代码，就不晕了**。

**误解二：「MLA 只是压缩 KV 的 trick。」** 压缩是收益，但结构上的洞察是「KV 展开形态的冗余」（32768 维活在 512 维子空间里）。吸收技巧说明这个压缩是**计算友好的**（降维点积）——很多压缩（如量化 KV）是计算中性的甚至负面的（反量化开销），MLA 是罕见的「压缩即加速」。结构级创新和工程级 trick 的分界线就在这：**前者同时改变多个系统层的最优解**。

**误解三：「FP8 会明显伤模型质量。」** per-block scale 的 FP8 在 LLM 推理端到端评测里几乎不可测（差异在评测噪声内）。真正的风险场景是极端数值（长尾激活、深层累积误差），生产用「关键层 FP16 + 其余 FP8」的混合精度兜底。**精度决策是收益/风险的工程权衡，不是信仰**——能看到评测数据之前，既不必恐慌也不必狂热。

**误解四：「通信重叠了就不需要优化通信本身。」** 重叠的前提是「计算时间 ≥ 通信时间」——通信时间砍半意味着更容易被覆盖（decode 侧计算极短，通信不砍就盖不住）。三板斧是相乘的：降通信量（FP8）× 降固定开销（低延迟内核）× 覆盖剩余（重叠）。**砍掉任何一环，另一环的负担都会涨回来**。

**误解五：「TileLang 会取代手写 CUDA。」** DSL 的编译器再聪明，通用热核的最后一成（10% 性能）仍要人手榨——这 10% 在每天亿万次调用的算子上就是巨额钱。分界线是「调用频次 × 单次收益」：热核人月级手写回本，长尾算子天级 DSL 快速迭代。两者是生态位互补，不是替代关系。

## 8. 小结

- **算子层定上限**：引擎层把输入的形状组织好，乘法发生在算子里；一个占 60% 时间的算子慢 20%，服务慢 12%。decode 侧一切优化的靶子都是第 01 章的「算术强度 2」。
- **GPU 执行模型一句话**：分块把数据从 HBM 上移到 SRAM/寄存器，并让每次搬运被摊销最大化——本章所有算子是这一个思想的四次代入。
- **MLA**：KV 活在低维子空间的洞察 → latent 压缩 57 倍 + 吸收技巧（结合律换序）让点积降到 512 维——「压缩即加速」的结构创新。
- **FlashMLA**：在线 softmax（分块重整化，数学严格等价）消灭中间矩阵 + decode 专用连续布局（200 请求拼大矩阵）——带宽利用率九成以上。
- **DeepGEMM**：满血模式（大 tile + TMA 双缓冲流水，MFU 60%+）与连续布局模式（1600 个 (token,专家) 对拼大 M，2%→60%）分别对应 P/D——架构分离在算子层的投影。
- **DeepEP**：MoE 瓶颈是两次 all-to-all。三板斧：双模式内核（低延迟内核砍协议栈/同步/拷贝三层固定开销）、FP8 传输（字节减半）、通信-计算重叠（先到先算）。合力让通信「消失」在计算里。
- **TileLang**：手写保底（热核榨干）+ DSL 提效（长尾快速迭代）的分界线是「调用频次 × 单次收益」。算子团队的效率是流水线不是个人英雄，最大时间投入是「证明没写错」（质量投资密度 ∝ 故障半径）。
- miniflow 三层结构（NumPy 参考/C++ 后端/自动回落）和四个教学点（循环序、融合、数值稳定、能力探测回落）把算子思想在 CPU 上复刻——**先写对的、再写快的、用前者当裁判**的工作流是最值得带走的。
- 「摊」的边界：数据的共享结构决定摊销空间（batch=1 超长上下文摊不动）——算子层、引擎层（造共享）、模型层（造压缩）各自摊各自的，合起来才是完整答案。

| kernel 融合 | 多个小算子合成一个，消启动开销和中间落显存 |
| TileLang | 算子 DSL：tile+循环+stage 抽象，生成近手写性能 |
| MFU / 带宽利用率 | 算力受限/带宽受限负载各自的满分标准 |

## 自测：开篇问题的参考答案

**Q1：MLA 为什么能压缩几十倍？** 结构洞察是「KV 的 32768 维展开形态活在 7168 维输入的像空间里，而有效信息集中在 512 维主子空间」——存 latent 向量 $c = W_{down}h$（576 数 vs 32768 数，约 57 倍），用 $W_{up}$ 恢复。压缩比来自「输入维度本身小于展开维度」+「训练证明的主子空间」。

**Q2：吸收的数学？** 结合律换序：$q^\top(W_{up}c) = (q^\top W_{up})c$。把升维矩阵预乘进现算的 Q，让每个历史 token 的 latent 直接参与 512 维点积（降 32 倍计算）——展开的 K/V 从未存在。

**Q3：在线 softmax？** 分块处理 K/V，维护运行状态 (max $m$、指数和 $l$、未归一化加权和 acc)，新块到来时按 $e^{m-m_{new}}$ 修正旧累积再累加新块——数学严格等价一次性 softmax（手算例子可验证），中间矩阵从不落显存，显存 $O(L^2)→O(L)$。

**Q4：DeepGEMM 的两模式？** 满血模式（prefill：M 上万的肥硕 GEMM，大 tile + TMA 双缓冲流水，MFU 60%+）；连续布局模式（decode：把 1600 个 (token,专家) 对按专家分组拼成连续大 M，从 2% 算力利用率拉到 60%——拼小为大的布局魔法，要求路由/通信/算子一体设计）。

**Q5：MoE 瓶颈为何是通信？** 每 token 只激活 37B/671B 参数，计算不重；但 dispatch/combine 两次 all-to-all 是「点对点 × N²」的碎通信——prefill 侧拼带宽（通信量随 token 线性涨）、decode 侧拼延迟（小消息的固定开销反客为主）。DeepEP 双模式内核（低延迟内核砍协议栈/同步/拷贝三层固定开销）+ FP8 传输（字节减半）+ 先到先算的重叠（通信被计算覆盖）。

**Q6：手写 vs DSL 的分界线？** 「调用频次 × 单次收益」：热核（MLA/GEMM/EP）每天亿万次调用，最后一成性能是人月级手写的回本；长尾新结构核用 TileLang 快速验证，跑赢再精修。生态位互补不是替代。

## 思考题

1. 用 0.4 节的摊销逻辑推 tile 尺寸的选择：64×64 tile 的算术强度约 64，128×128 约 128——为什么不满无限大（三个约束：SRAM 容量、张量核的碎片尺寸、占用率/并行度）？查一下 H800 的共享内存上限，算 128×128 FP16 双缓冲要多少 SRAM。
2. 手算验证吸收技巧：设 $q = [1, 0]$，$W_{up} = \begin{bmatrix} 2 & 1 \\ 0 & 3 \end{bmatrix}$，$c = [1, 1]$。分别算 $q^\top(Wc)$ 和 $(q^\top W)c$，确认相等。然后想：如果 $W_{up}$ 是 32768×512、批内 200 条请求，恢复路径和吸收路径各自要做多少次乘加？
3. 在线 softmax 手算题：分数序列 $s = [2, 5, 3]$，V = [4, 6, 8]，按 [2] 和 [5,3] 两块处理。逐步写出每块的 (m, l, acc) 更新，最后归一化输出；再和一次性 softmax 对答案。若把分块改成 [2,5] 和 [3] 呢——结果变吗？
4. DeepGEMM 连续布局的前提是「路由统计已知」。但路由是逐 token 现算的（每个 token 过完路由器才知道去哪）——「拼接连续内存」发生在哪个时间点（提示：dispatch 的发送端就按专家分组排布，接收端零拷贝）？这个设计要求路由器的输出格式是什么（提示：分组索引 + 偏移表）？
5. DeepEP 低延迟内核砍掉了「同步等待全员」。代价是什么（提示：钩子式推进意味着各卡的MoE 计算不再是同一时刻开始——第 02 章确定性目标的哪个泄漏源被触碰了？怎么在「先到先算」和「确定性归约」之间调和）？
6. 动手题：跑 miniflow 的 `matmul_naive` vs `matmul` 基准（`python -c "from miniflow.tensor import matmul_naive, matmul; ..."` 自造 512×512 随机矩阵计时）。然后手写 jki 序的第三种实现，三者的差距和「B 按列/按行访问」怎么对应？再把矩阵换成 4096×4096，差距怎么变（缓存放不下整矩阵时，局部性的价值更大还是更小）？
7. 通信底座题：3.7 节的「时代三」轮询直达要烧 CPU 核盯网卡。算一笔账：64 卡集群每卡留 2 个核做轮询，全集群烧掉多少核？这些核如果不轮询，能干什么（提示：调度器、采样、块管理都是 CPU 活——第 07 章 CPU/GPU 流水线）？这个「核预算」的分配是架构决策，你怎么分？
8. 用「三条路线」的框架（减 KV / 换算法 / 换表示）给你知道的其他注意力变体分类：Multi-Query（哪条路）、Mamba（哪条）、KV 量化到 INT8（哪条）、滑动窗口（哪条）？每条路线的「药理」和「代价」各用一句话总结。分类不出来的（混合路线）也标出来——例如 MLA+滑窗的组合现在有人做，它想同时拿什么好处？
9. TileLang 实验：仓库里 `csrc/kernel.cpp` 的 fused_silu_swiglu 是「融合」的最小标本。把它拆回三个独立算子（silu、乘法、写回）分别计时，和融合版对比中间张量的写读开销。用 4096×4096 的输入，预估「省一次往返」值多少毫秒——再对照第 01 章「算一笔账」的 11 ms，感受 CPU 和 GPU 上同一思想的数量级差。
