# 09 采样：确定性与批次不变

模型 forward 的产物是 **logits**——词表里每个 token 的打分。从打分到一个确定的输出 token，中间要经过**采样**这一步。本章先把这个流程完整讲一遍（初学者需要），再讲本章真正的主角：为什么「同一条请求的输出」会偷偷依赖「批里其他请求是谁」，以及 DeepInfer 怎么把这种泄漏全部拆掉。

采样的代码量在引擎里占比极小（几百行），但它坐在「模型的随机性」和「系统的确定性」的交界上——所有「可复现」「可测试」「可审计」的工程能力都从这里发端。本章的立场延续第 02 章：**确定性是设计目标不是默认状态**——每一条泄漏都要主动拆。

读完本章，你应该能回答：

- 四道工序（temperature/top-k/top-p/采样）各自的数学和在改变什么？
- 温度 T→0 和 T→∞ 的极限行为各是什么？
- 三处批维泄漏（归约顺序/top-p 截断/RNG 流）各自的机理？
- 逐请求 RNG 为什么种子要混入 seq_id？为什么消费次数必须恒定？
- greedy 是不是免费的 batch-invariant？

## 1. 采样的完整流程

从 logits 到 token，依次经过四道工序。

### 1.1 先认识 logits

forward 的最后一层输出一个 $|V|$ 维向量（$|V|$ = 词表大小，DeepSeek 约 12.8 万）——每个分量是那个 token 的**未归一化打分**，这就是 logits。三个关键性质：

- **相对量才有意义**：logits 的绝对值无意义（可以整体平移不改变 softmax 结果），只有相对差有意义——差 2.0 意味着 $e^{2.0} \approx 7.4$ 倍的几率比；
- **无界**：可以任意大/小（所以直接 softmax 有数值溢出风险——见 1.2 的 max 技巧）；
- **「模型的意见」到此为止**：logits 之后的一切（温度、截断、采样）是**系统的决策**——同一个模型接不同的采样策略，行为截然不同。**「模型」和「采样器」的边界就在 logits 上**。

### 1.2 工序一：temperature（温度）

把 logits 除以 $T$ 再 softmax：

$$
p_i = \frac{e^{l_i / T}}{\sum_j e^{l_j / T}}
$$

$T$ 越低，分布越尖锐（趋近 argmax 的贪心选择）；$T$ 越高，分布越平（低分 token 也有机会）。$T=0$ 约定俗成为贪心——直接取 argmax，无随机性。直觉上温度控制的是「模型有多敢冒险」。

用数字感受（三个 token，logits [3.0, 2.0, 1.0]）：

```text
T=0.5:  p ≈ [0.865, 0.117, 0.016]   —— 尖锐，基本选第一名
T=1.0:  p ≈ [0.665, 0.245, 0.090]   —— 模型的"原生"意见
T=2.0:  p ≈ [0.506, 0.297, 0.197]   —— 平坦，第二名也常中
T→∞:    p → [1/3, 1/3, 1/3]          —— 均匀，模型意见被抹掉
```

两个极限的直觉：**T→0 是「模型的独裁」**（再小的分数差也被指数放大成压倒性优势），**T→∞ 是「模型的罢工」**（多大的分数差也被压缩成近似均匀）。生产的常用区间 0.1~1.5：代码生成用低温（0.1~0.3，正确性优先）、创意写作用高温（0.7~1.2，多样性优先）、agent 调用居中（0.3~0.7）。

顺带一个数值细节（第 04 章 `softmax` 教学点的呼应）：直接算 $e^{l_i}$ 会溢出（logits 上百时 $e^{100}$ 是天文数字）——**先减去行最大值再指数化**（$\frac{e^{l_i - m}}{\sum e^{l_j - m}}$，数学等价、数值稳定）。这个「减 max」的技巧和第 04 章在线 softmax 的 running max 是同一个思想在不同粒度的应用——**数值稳定的手法在算子层和采样层各出现一次**。

### 1.3 工序二：top-k

只保留分数最高的 k 个候选，其余概率清零。防止长尾 token（词表里几万个几乎不可能的词）偶尔被抽中。

「偶尔抽中」为什么是问题？算一笔：词表 12.8 万，top-50 之外的单个 token 概率或许只有 $10^{-5}$——但**尾部合计**可能有 1~5%。一个 1000-token 的回答，尾部被抽中的概率是 $1-(1-0.03)^{1000} \approx 1$——**几乎必然出现至少一个离谱 token**（乱码、不相干的词、突然的语种切换）。top-k=50 把尾部整体归零，代价是把「正确的冷门词」也归了零（专有名词、代码里的罕见标识符）。

### 1.4 工序三：top-p（nucleus）

按分数从高到低累加概率，到达 p（如 0.9）就截断——保留「累计概率 p 的最小集合」。比 top-k 聪明的地方：候选数随分布形状自适应——确信时留 2 个，犹豫时留 50 个。

数字例子：

```text
分布 A（模型很确定）：p = [0.93, 0.04, 0.02, 0.01]
  top-p 0.9 → 保留 1 个（0.93 已超线）——高置信时更贪心
分布 B（模型犹豫）：p = [0.30, 0.28, 0.25, 0.10, 0.07]
  top-p 0.9 → 保留 4 个（累计 0.93）——犹豫时保留多样性
```

同一个 k=4 对分布 A 浪费（3 个陪跑）、对分布 B 可能不够（截掉了 0.07 的合法候选）——**top-p 的自适应性是「按置信度调多样性」**，这是它取代固定 k 成为主流的原因。生产上 top-p 0.9~0.95 + temperature 0.7 是聊天模型的经典组合（先 top-p 拦尾部、再温度调锐度——顺序见 1.6）。

### 1.5 工序四：采样

按最终归一化的分布抽一个 token——就是轮盘赌：在 [0,1) 上均匀抽个数 $u$，沿累积分布走，落在哪个区间选哪个 token。这一步是**随机性的唯一入口**（前三道工序都是确定性的变换）——第 3 节的「RNG 泄漏」就藏在这里。

### 1.6 四道工序的顺序：为什么是这个序

temperature → top-k → top-p → 采样，这个固定顺序值得问一句为什么——**顺序换了，语义就变**：

- **temperature 在最前**：它改变分布的形状（锐化/平滑），必须在截断类操作之前——先用温度定型「模型意见的锐度」，再谈截谁。若 top-k 在前，截断的是「未调温」的排名——T 调高时被截掉的集合不随之变，语义错乱；
- **top-k 在 top-p 之前**（两者都开时）：先粗截（固定数）再细截（按累计）——k 拦绝对长尾、p 调自适应窗口，作用不重叠；
- **采样在最后**：随机性只能出现一次、出现在最终分布上——任何「截断后再改分布」的操作都会让「抽中概率」和「名义分布」脱钩（审计性破坏）。

一个通用的顺序原则：**确定性变换在前、随机性在后**——前面的工序改变「抽签的签筒」，最后的采样只是「摇一次」。把任何随机操作挪到前面（比如先随机截断再调温），复现和审计都会碎掉。

这四道工序里每一道都可能出现「批维泄漏」——同样的 logits，因为批里邻居不同而走到不同结果。这不是假设，是常规实现的常态。

## 2. 问题：批组成是一个隐藏变量

常规实现为了效率，把整批请求的 logits 拼成一个大矩阵统一处理——softmax 按矩阵行做归约、top-p 按批排序、随机数从共享流里抽。三个后果：

**浮点求和顺序随批形状变。** softmax 的分母是对整行求和。批形状（多少条请求、各自多长）变化时，底层归约的**分块方式**变化，加法的结合顺序变化——而浮点加法**不满足结合律**（$(a+b)+c$ 与 $a+(b+c)$ 在最后几位上可以不同）。

### 2.1 一位 ULP 怎么演变成完全不同的输出

「最后几位不同」听起来无害，值得把放大链完整走一遍——它是第 02 章「ULP→输出分岔」的详细版：

```text
第 0 步：softmax 分母 1.0000000001 vs 1.0000000000（1 ULP 差）
第 1 步：p(「苹果」) = 0.30000000003 vs 0.29999999997
第 2 步：累积分布的边界点漂移 10^-10 —— 但轮盘赌的 u 落在边界附近 10^-9
        以内时，两次运行选不同 token（概率小但 1000 步里总会撞上）
第 3 步：一旦翻面，下一个 token 的输入就不同 → logits 完全不同
        → 后续 999 步在两条完全不同的轨迹上
第 4 步：输出文本从「今天聊聊苹果的做法」变成「今天聊聊橙子的保存」
```

第 2 步的「撞边界」是关键放大器：**边界概率虽然小，但每步都有机会，序列长了必然命中**（$1-(1-\epsilon)^{1000}$，$\epsilon=10^{-4}$ 时命中概率 10%）。**单步的无害误差 × 长序列 = 必然的分岔**——这是所有「浮点非确定性在 LLM 上是真问题」的数学根据。

**top-p 的截断受邻居影响。** 如果实现把批内排序/截断做成整批操作，「哪些 token 进入候选集」就可能掺入邻居的信息。比如「按整批的 logits 排名取前 N」——你的候选集取决于别人的分数分布，**邻居的「词穷」改变你的「候选」**。

**随机数流被邻居消费。** 全局共享的 RNG：批里排在前面的请求先抽走随机数，我的起点就变了。换个邻居、换个顺序，我抽到的数全变。

合起来：「换一批邻居、换个批大小、换个到达顺序 → 输出漂移」。生产上的真实代价：

| 场景 | 后果 |
|---|---|
| 回归测试 | 同输入不同输出 → 测试红绿灯失灵 |
| A/B 实验 | 采样噪声混进策略对比 → 结论失真 |
| 分片重放 | 按请求分片重跑与在线对不齐 → 审计困难 |
| 故障定位 | 「昨天好好的今天变了」→ 排查方向被带偏 |

DeepInfer 把这当**正确性**问题处理（QA 文档明确列为部署要点），而不是「尽量做好」的工程偏好。

### 2.2 一个可以亲手复现的实验

「批组成影响输出」抽象难感，值得一个具体实验（miniflow 的 `MF_BATCH_INVARIANT=0` 模式就是为此保留的）：

```bash
# 第一次：请求 A 单独跑
python examples/offline_inference.py --prompts "写一句关于春天的诗" --seed 42

# 第二次：请求 A 和一堆干扰请求拼批跑
python examples/offline_inference.py --prompts "写一句关于春天的诗" "闲聊1" "闲聊2" ... --seed 42
```

关闭 batch-invariant 时，两次的「春天的诗」**不同**（邻居改变了 A 的归约顺序和 RNG 位置）；开启后**逐 token 相同**。这个五分钟实验比十页论证更有说服力——**坏行为的现场演示是最好的教学**，miniflow 特意保留这个「坏开关」的原因。

## 3. 拆除三处泄漏

miniflow 的 `miniflow/sampler.py` 逐条拆除，代码即文档：

```python
# 泄漏一：随机流
#   坏：批级共享 RNG —— 批大小变化 => 每条请求消费的随机数错位
#   好：每序列独立 RNG，种子 = [seq_seed, seq_id]
rng = np.random.default_rng([int(seed), int(seq.seq_id)])

# 泄漏二：归约顺序
#   坏：整批 logits 矩阵统一 softmax —— 浮点求和顺序随批形状变
#   好：逐请求独立归约（softmax/top-p 只在自己那行 logits 上做）

# 泄漏三：过滤截断
#   坏：top-p 按批排序截断 —— 邻居的分布影响我的候选集
#   好：top-k/top-p 截断只看本请求的 logits
```

三条拆除的代价值得诚实列出（没有免费的确定性）：

- **逐请求归约**放弃了批级 softmax 的向量化（NumPy/GPU 上「一行一个 softmax」比「大矩阵一次算」慢 2~5 倍）——采样只占 step 耗时的一两个百分点，所以绝对代价小，但**比例上是最贵的一段代码**；
- **逐请求 RNG** 放弃了全局 RNG 的流水复用（每请求一个 RNG 状态的创建/恢复有纳秒级开销）——量级可忽略；
- **逐请求截断**放弃了跨请求的排序合并（top-p 各排各的）——同上可忽略。

注意三条的代价量级悬殊（归约是真贵、另两个几乎免费）——**确定性的成本集中在「计算归约」一处**，这也是为什么第 02 章说确定性总代价「个位数百分比」：大头只有一处，其余是结构性的免费改进。

还有一个不起眼但承重的细节——**RNG 消费次数恒定**：每步采样恰好消费 1 个随机数。于是即使请求被抢占、回等待队列、重新 prefill、被调进另一个批，它的随机流也**不错位**——每生成一个 token 消耗一个数，账目和进度严格同步。这是「重调度不变性」的最后一环（第 5 节展开）。

「恒定消费」的反面教材：某些实现里「top-k 截断后再 rejection sampling」——被拒后**再抽一次**（消费 2+ 个随机数）——被拒率随分布形状变，随机数消费就变，**「抽到什么」依赖「第几次抽」**。修复要么先算好接受概率一次成型（Gumbel 技巧），要么把 rejection 的随机数也走独立流。**RNG 的协议要像 KV 的进度一样精确记账**——这两套「账本」（KV 进度、随机数进度）是请求可恢复性的两大支柱。

## 4. 确定性组合拳

DeepInfer QA 的表述（miniflow 复刻为 README 的第一公式）：

```text
batch-invariant 推理 + 固定 seq_seed + 关闭推测解码
    => 相同输入 token 必得相同输出 token
```

三个开关各管一段：**batch-invariant** 把批组成从输出函数的变量集里剔除（第 3 节的三处拆除）；**seq_seed** 把随机流显式化——用户可指定、默认 0、不留隐式状态（「种子藏哪了」是复现失败的头号原因）；**关闭推测解码**是因为 spec 的 draft 自带额外随机性（教学版用 argmax 验证是例外，见 [第 08 章](08-speculative.md)）。

!!! note "greedy 是 batch-invariant 的免费特例"

    temperature=0 时输出 = argmax(logits)，纯函数、无随机——但注意
    前提仍然是**逐请求独立归约**：整批矩阵归约的浮点顺序变化同样能
    翻动 argmax 的选择。miniflow 的 `test_batch_composition_invariant`
    同时测 greedy 与带温度两条路径，就是要钉死这一点。

greedy「不免费」的机理值得单独看：argmax 对「并列最高分」的 tie-break 是实现定义的（NumPy 取第一个、别的库可能不同）——**并列时的选择顺序若依赖批布局（比如按批内偏移遍历），批组成就渗进了 greedy**。逐请求归约（在自己的 12.8 万维向量上 argmax、固定的遍历序）把 tie-break 也钉死——**greedy 的不变性同样是「隔离」买来的，随机性消失只是少了一个泄漏源，不是全部**。

### 4.1 确定性 vs 多样性：API 设计的分寸

「所有输出可复现」和「产品需要多样性」有张力——API 层怎么平衡？业界的惯例分三档：

- **默认档**：seed 由服务端生成、随响应返回——同 seed 重放可得相同输出（复现能力），不同次调用不同 seed（多样性）。**复现是能力不是默认**；
- **用户指定档**：`seed` 参数显式传入——测试、审计、A/B 的场景。服务端要保证「同 (input, seed) → 同 output」跨任何部署状态成立（本章全部内容）；
- **探索档**：seed 固定 + temperature 拉高——「同一个起始宇宙的平行样本」，用于数据合成（可控多样性：分布相同、样本不同）。

三档共用同一个机制（显式 seed + 逐请求 RNG），差别只在 seed 的来源——**「多样性」和「可复现」不冲突，冲突的是「隐式随机」**。把随机性显式化（seed 进 API）后，两端兼得。

## 5. 序列种子：为什么混入 seq_id

```python
np.random.default_rng([seed, seq_id])
```

为什么种子不只是用户的 seed，还要拼上序列号？考虑对照组实验：两条**内容相同**的请求用同一个 seed 发进来——不混 seq_id 的话，它们会派生出**相同的随机流**，输出完全一样的文本。这恰好制造了「内容相同 → 输出相同」的伪相关，污染实验结论。混入 seq_id 后，同 seed 的请求各自独立采样；而不同 seed 的请求天然独立。用户想要的「同请求同结果」由 [seed, seq_id] 的二元组唯一保证。

seq_id 混入的另一个收益：**重试的语义正确**。客户端超时重发同 seed 的请求——seq_id 不同（新请求），输出**不同**（新样本）。若不混 seq_id，重试得到完全相同的输出——「重试了但内容一样」，用户困惑「到底重试成功没」。混入后每次重试是独立采样，重试的行为语义（「再要一个样本」）正确表达——**seq_id 是「请求身份」在随机性世界的投影**。

`MF_BATCH_INVARIANT=0` 环境变量可以关闭整套机制——刻意保留一个「坏的对照组」，用来演示批组成如何影响输出（对应 DeepInfer 的 `DEEPINFER_*` 环境变量开关体系）。**看得见坏行为，才真正理解好设计**。

### 5.1 [seed, seq_id] 之外的第三维：step 吗

一个自然的疑问：为什么 RNG 不需要混入 step（第几步）？——因为**流本身是有序的**：`default_rng` 派生的流按抽取顺序推进，第 n 次抽取天然对应第 n 个 token。「恒定消费 1 次/步」+「流有序」= step 隐式编码在抽取序里。混 step 反而破坏这个性质（每步都「重置」到 (seed, seq_id, step) 的独立流——也能用，但流的语义从「序列」变「集合」，和「重调度后接上」的协议冲突）。**「有状态的流」优于「无状态的重散列」**——前者免同步、天然续接，这是 RNG 设计的隐藏智慧。

## 6. 与其他子系统的协议

采样是多个子系统的交汇点，每个交互都有一条精确协议：

| 交互方 | 协议 |
|---|---|
| 推测解码 | `sample_one(seq, logits)` 单序列路径与批量路径共用同一 RNG 派生规则——spec 采样不错位 |
| 结构化输出 | mask 在**采样前**施加（非法 token 置 `-inf`），softmax 在掩码后归一化——约束不扭曲合法部分的分布形状（[第 10 章](10-structured.md)） |
| 抢占/重调度 | RNG 每步恒定消费 1 次 → 重调度后随机流从上次位置继续 |

第三条最容易被忽视：请求被抢占 → 回 waiting → 重新 prefill → 继续 decode，中间经历任意次调度变化，它的随机流**依然接得上**。「逐请求随机流」和「恒定消费」两件小事合起来，才是完整的重调度不变性。

spec 的协议值得再点一句（第 08 章的衔接）：verify 的接受/拒绝判定**不消耗**请求的 RNG（那是确定性的 logits 比较），只有「最终 token 的采样」消耗——所以 spec 开关不影响随机流的步进。但拒绝后的**残差采样**要消耗——而且残差分布每次不同，**「同 seed 下 spec-on 和 spec-off 输出不同」**（第 08 章误解三的机理在此）——组合拳要求「复现时 spec 开关状态一致」的根源。

## 7. 常见误解澄清

**误解一：「采样就是 softmax。」** softmax 只是四道工序的第一道（还是和温度合在一起的那道）。完整的采样器是「温度→截断→抽签」的管线，每道都有独立的语义和参数——把「采样」说成「softmax」相当于把「烹饪」说成「点火」。

**误解二：「temperature=0 就完全确定。」** 对**随机性**成立（无抽签），对**批不变性**不成立（argmax 的 tie-break 和归约顺序仍可泄漏——4 节的 note）。greedy 减少一个泄漏源，不是免疫——「没有随机数」和「同输入同输出」是两个命题。

**误解三：「top-k 和 top-p 差不多，用哪个都行。」** 固定 k 在「模型置信度变化」时行为不一致（高置信时浪费、低置信时误截）——top-p 的自适应是按分布形状调窗口。差别在尾部场景放大：**top-k 50 在「模型 99% 确信」时保留 49 个陪跑（浪费不大但语义错误），在「模型五五开」时可能截掉合法候选**。生产主流已迁 top-p，top-k 保留在需要「绝对上限」的合规场景（保证候选数 ≤ k 的审计要求）。

**误解四：「确定性采样器会拖慢引擎。」** 三条拆除里只有「逐请求归约」有真实代价（采样段慢 2~5 倍，但采样只占 step 的 1~2%）——**总账个位数百分比**。且这个代价换来的回归测试/A/B/重放能力（第 02 章）在工程体系的估值远超几个百分点吞吐——「确定性贵」的直觉停留在采样段局部，没有算系统的总账。

**误解五：「seed 传了就能复现。」** 复现是三开关的合取：batch-invariant（拆泄漏）+ seed（显式随机源）+ spec 状态一致（第 8 章）——**只传 seed 是必要不充分**。「我传了 seed 还是不可复现」的排查清单：先查批不变开关、再查 spec、最后查模型版本——按泄漏的隐蔽度排序。

## 8. 小结

- **采样四道工序**：temperature（定型锐度——T→0 独裁、T→∞ 罢工）→ top-k（拦绝对长尾）→ top-p（自适应窗口——按置信度调多样性）→ 抽签（随机性唯一入口）。**确定变换在前、随机在后**的顺序是复现/审计的地基。
- **logits 是模型和系统的边界**：之前的误差是模型的、之后的漂移是系统的——采样器的确定性工程全部在边界之后。
- **三处批维泄漏**：浮点归约顺序（ULP × 长序列 = 必然分岔）、top-p 整批截断（邻居的词穷改我的候选）、共享 RNG（邻居抽走我的随机数）。拆除 = 逐请求的归约/截断/RNG——代价集中在归约一处（总账个位数百分比）。
- **RNG 的完整协议**：种子 [seed, seq_id]（重试语义 + 对照组独立性）、恒定消费 1 次/步（重调度续接）、流有序（step 隐式编码，勿重置）。**随机数账本和 KV 进度账本是可恢复性的两大支柱**。
- **确定性组合拳**：batch-invariant + 固定 seed + spec 状态一致 ⇒ 同输入同输出。greedy 是「少一个泄漏源」不是免疫（tie-break 仍需隔离）。多样性靠显式 seed 的三档 API（服务端默认/用户指定/探索档）与复现兼得。
- **坏开关的教学价值**：`MF_BATCH_INVARIANT=0` 留着——**看得见坏行为才懂好设计**。

## 思考题

1. 手算温度：logits [4.0, 2.0, 0.5]，分别算 T=0.3、1.0、3.0 的 softmax（减 max 技巧先做）。哪个温度下第三名 token 几乎无机会？「温度让第三名回到牌桌」大约需要 T 多大——这解释了为什么创意写作的 T 很少超过 1.5（再高就「语无伦次」了）？
2. 1.6 节说「顺序换了语义就变」。构造一个具体例子：top-p 在 temperature 之前做，T 从 0.5 调到 2.0 时候选集的行为和正确顺序有什么不同（提示：先截断后调温，截断集是「原始分布的 top-p」——T 调高后抽签分布和截断集错配，可能出现「名义候选概率和 <1」或「被截的 token 在调温后其实不弱」）。写出两种顺序下 p(top1 被选中) 的表达式对比。
3. 2.1 节的放大链：$\epsilon=10^{-4}$ 的单步翻面概率、1000-token 序列的分岔概率算出来是多少（$1-(1-\epsilon)^n$）？如果要「分岔概率 <1%」，单步 $\epsilon$ 要压到多小——这对应浮点误差要压到几位有效数字？由此论证「逐请求归约不是过度设计」。
4. 5.1 节的「流 vs 重散列」：如果实现改成 `rng = default_rng([seed, seq_id, step])`（每步独立流），重调度不变性还成立吗（提示：流无状态，每步独立——重调度天然无影响）？那它牺牲了什么（提示：两个「相邻 token」的随机数独立性——流版本里相邻抽取有伪随机相关性，重散列版完全独立；哪个对「采样的统计质量」更正确？查一下 PRNG 流的子序列性质）？
5. API 设计题：你的产品要加「温度推荐」功能——按用户输入的类型（代码/闲聊/写作）自动选 temperature。你会用什么信号分类（提示：结构化输出请求天然低温——第 10 章的约束和温度的交互；长上下文的 agent 请求呢）？给出一个初版规则表和它的失效场景。
6. 动手题：跑 2.2 节的对照实验（`MF_BATCH_INVARIANT=0` + 不同批构成，同 seed）。记录两次输出的第一个分岔位置（第几个 token）——它是边界命中的位置。再跑 10 组，看分岔位置的分布：集中在早期还是均匀分布？这和 2.1 节的「概率随步数累积」一致吗？

!!! danger "测试中的一个真实发现"

    `test_seed_changes_output` 初版在 temperature=1.0 下断言「换 seed
    输出不同」——**失败**：400 步过拟合的小模型分布接近 one-hot，
    任何种子的采样都落在 argmax 上，seed 的作用不可观测。
    教训：确定性测试要确保被测变量真的进入了输出函数——最终
    temperature 提到 2.5 摊平分布才测出差异。低温下「看起来确定」
    和「真的确定」是两回事。

这个踩坑值得一层展开：**「变量不可观测」是测试的假阴性**——断言通过了，但它测的是「分布退化为 argmax」而不是「seed 有效」。两类错误（假阳性/假阴性）里，假阴性更阴险：测试绿着，能力却不存在（换个不退化的模型，seed 功能坏了都没人知道）。防御方法：**测试要验证「变量有杠杆」**——先断言「温度 2.5 下不同 seed 输出确实不同」（seed 的可观测性），再断言「同 seed 复现」（seed 的作用）。**先证伪能力存在，再验证行为正确**——这个顺序对所有参数化机制的测试都适用。

## 10. 一个完整的采样调用：逐行走查

把四道工序 + 三处拆除在一段（简化的）真实代码上走一遍——`miniflow/sampler.py` 的骨架：

```python
def sample_tokens(self, seqs, logits_batch):
    # 输入：本批的序列列表 + 各自的 logits（batch × vocab 的矩阵）
    out = []
    for seq, logits in zip(seqs, logits_batch):     # ← 逐请求（拆泄漏二/三）
        # 工序 0：结构化掩码（第 10 章，非法 token 置 -inf）
        if seq.constraint is not None:
            logits = seq.constraint.mask(logits)     # ← 采样前施加（协议）

        # 工序 1：温度
        if self.temperature == 0.0:
            token = int(np.argmax(logits))           # ← greedy 路径
        else:
            scaled = logits / self.temperature

            # 工序 2+3：top-k / top-p（只看本行）
            if self.top_k:
                idx = np.argpartition(-scaled, self.top_k)[:self.top_k]
                mask = np.full_like(scaled, -np.inf); mask[idx] = scaled[idx]
                scaled = mask
            if self.top_p:
                order = np.argsort(-scaled)          # ← 本请求内排序（拆泄漏三）
                csum = np.cumsum(softmax_stable(scaled[order]))
                keep = csum <= self.top_p + 1e-9
                # …截断…

            # 工序 4：抽签
            probs = softmax_stable(scaled)
            rng = self.rng_for(seq)                  # ← [seed, seq_id] 派生（拆泄漏一）
            token = int(rng.choice(len(probs), p=probs))   # ← 恰好消费 1 次

        out.append(token)
    return out
```

五行注释对应本章的全部要点：`for` 循环的「逐请求」拆掉泄漏二和三（归约和截断都在自己行上）；`rng_for(seq)` 拆掉泄漏一；`constraint.mask` 在温度**之前**（第 10 章的协议）；`rng.choice` 恰好消费一次（重调度续接）。**四个泄漏点 + 一个协议点，全部在 20 行代码里各有自己的位置**——读任何采样器实现，先找这五个位置。

（`softmax_stable` 就是 1.2 节的「减 max」版本——它也在这 20 行里，第 04 章的算子级技巧和本章的采样级技巧在这里会师。）
