# 02 三大设计目标

第 01 章说过，推理服务被三个指标拉扯：TTFT、TPOT、吞吐。本章把它们升级为三个**设计目标**——低延迟、高吞吐（= 低成本）、确定性——并讲清楚每个目标真正的难点在哪、手段为什么有效、以及它们为什么互相打架。DeepInfer 的每个子系统都能挂回这三个目标；以后你看到任何一段代码感到「为什么这么绕」时，回到这章找它服务的目标。

## 目标一：低延迟

用户对「快」的体感由两个数决定，第 01 章已经定义过：**TTFT**（发出请求到看到第一个字）和 **TPOT**（之后每个字的间隔）。它们看似都是「延迟」，实际由两个完全不同的计算环节决定，优化手段几乎没有交集——这是本章最重要的认知：

**TTFT 由 prefill 决定。** 收到请求后，引擎要先把整段 prompt 一次性前向完（这步叫 prefill，因为是在为生成「填充」KV Cache），才能吐出第一个 token。prompt 有 10000 个 token，这就是一次 10000 个位置的大矩阵乘。注意它和 decode 的本质区别：prefill 一次算成百上千个位置，算术强度高，是**计算受限**的，GPU 的算力能吃满。

**TPOT 由 decode 决定。** 之后每步只算 1 个位置，第 01 章算过账：带宽受限，芯片在等数据。

一个计算受限、一个带宽受限，混在同一个 GPU 上就会互相伤害——prefill 的大矩阵乘会占满计算单元，让排队中的 decode step 干等；反过来一堆小 decode step 也让刚启动的大矩阵乘频繁让路。所以 DeepInfer 的手段从「加速」转向「隔离」：

- **P/D 分离**（[第 03 章](03-architecture.md)）：prefill 和 decode 分别部署到不同节点群，各自按自己的瓶颈调优——prefill 节点堆算力，decode 节点堆显存带宽和容量；
- **chunked prefill**（[第 07 章](07-scheduler.md)）：无法分离部署时（单机场景），把一段长 prefill 切成小块，每算一块就插一步 decode，让正在生成的请求不被饿死。代价是这段 prefill 自己变慢——所以它是在 TTFT 和 TPOT 之间按需调权的开关。

还有一个容易被忽略的 TTFT 杀手：**结构化输出的编译**。如果用户要求输出匹配一个复杂的 JSON Schema，引擎要把 schema 编译成语法自动机（[第 10 章](10-structured.md)），复杂 schema 的编译可能要几百毫秒——如果这段编译阻塞在第一个 token 之前，用户就在界面上干等。DeepInfer 的做法是把编译放到专用的机器上异步执行，decode 侧拿到编译结果之前先按「无约束」跑着，拿到后才开始施加约束。

## 目标二：高吞吐

同样的硬件，单位时间产出多少 token。这项指标直接换算成成本：8 块 GPU 的集群，吞吐翻倍等于每个 token 的成本减半。

### 延迟和吞吐在哪里打架

第 01 章说过组批是带宽矛盾的解药，但组批有一个副作用：**batch 越大，单条请求的 TPOT 越差**。同一块 GPU 的带宽是固定的，batch=64 时 64 条请求的 KV Cache 读取分抢同一条总线，每条请求等到的数据都晚了一些。

但关键在于恶化的**速度**：TPOT 并不随 batch 线性变差。权重读取是全批共享的（读一次服务 64 条请求），只有 KV Cache 部分随请求数增长。假设权重 37 GB、每条请求 KV 平均 1 GB，那么 batch=1 时每步要搬 38 GB，batch=64 时搬 37+64=101 GB——搬运量只涨到 2.7 倍，但产出 64 个 token，**单 token 成本降到 1/24**。所以吞吐随 batch 增长远快于 TPOT 恶化，大 batch 几乎总是划算的——前提是你有那么多请求可拼、显存放得下这么多并发请求的 KV Cache。这两 个前提分别是调度器（第 07 章）和分页 KV（第 06 章）的战场。

### DeepInfer 提吞吐的三个手段

**E/P/D 分离部署**：prefill 节点专心拼大 batch 吃满算力，decode 节点把 KV Cache 驻满、带宽跑满。两类负载各自趋近最优，不再互相污染。

**前缀缓存 + 3FS 持久化**（[第 06 章](06-kvcache.md)）：大量流量共享同一段 system prompt。这段的 KV Cache 只需算一次，之后所有请求直接复用——省下的 prefill 算力就是白捡的吞吐。3FS 更进一步：把 KV 落到分布式文件系统，跨请求、跨时间段复用（TTL 3~7 天），连「不同时刻到达的请求」都能共享。

**推测解码**（[第 08 章](08-speculative.md)）：DSpark 的生产数据是变长验证带来 +4~7% 吞吐。听起来不大，但注意它的性质：**纯软件优化换来等效扩容**——不加一台机器，4~7% 的服务成本就没了。在百万 token 服务的规模下，这就是一笔大钱。

### 提醒：吞吐数字的水分

看到一个「XX tokens/s」的宣称，要能问出三个问题：什么模型（参数量决定每 token 的搬运量）、什么长度分布（prefill 重还是 decode 重）、什么并发（batch 拼到多大）。prefill-heavy 和 decode-heavy 两种流量的吞吐能差数倍。DeepInfer 内部用一个拟合的成本模型 cost(q, c)（q 为 chunk 大小、c 为并发）量化「prefill 和 decode 混跑一台机器」的损失，用数据决定分还是混，而不是拍脑袋。

## 目标三：确定性与可控性

前两个目标是所有框架共有的，这一个最能区分「跑 demo」和「跑生产」。它说的是：**同一条请求，输出只取决于（输入, 种子），与它恰好在哪个 batch 里、邻居是谁、服务器负载多高，全都无关。**

### 为什么「默认做不到」

初学者通常以为这是天然成立的——毕竟模型权重是固定的。但有两个隐蔽的泄漏源：

**浮点加法不满足结合律。** $(a+b)+c \neq a+(b+c)$，误差在浮点下不同。框架为了效率会把同批多条请求的张量拼在一起做 reduction（比如 softmax 的分母求和），批里多了谁、顺序怎么排，都会改变求和的运算顺序，进而改变每一位低有效数字——放大几千层后，输出 token 就可能完全不同。

**随机数流是全局的。** 采样要从分布里抽随机数，如果全进程共享一条随机数流，批里邻居请求先抽走了几个数，我的随机数就变了——「和我拼批的请求是什么」影响了我抽到什么。

所以 batch-invariance 不是「把 seed 固定」就完事，必须**拆除这两个泄漏**：归约顺序与批组成解耦（每条请求独立归约，或用顺序无关的求和），随机流按请求隔离（每条请求从自己的 seed 派生独立流，[第 09 章](09-sampling.md) 有完整设计）。

### 生产为什么需要它

- **回归测试**：改了一版调度器代码，跑一遍测试集，输出必须和改动前一致，否则你分不清是 bug 还是抖动；
- **A/B 对比**：对比两个参数的效果，如果输出随批组成漂移，对比结论就是噪声；
- **分片重放**：把线上流量切片重放排查问题，切片方式和线上不同就不能对齐。

围绕这个目标还有两个相关能力：**结构化输出**（Agent 要求输出严格匹配 JSON Schema，第 10 章）和**特殊 token 防注入**（用户输入里字面的控制标记不能改变模型行为分界，第 11 章）。它们共同的底层思路：把「输出必须满足的约束」做成系统保证，而不是祈祷模型自觉。

## 三个目标的共同底层：把状态管起来

分别看完三个目标，退后一步会发现一件事：它们的最强手段全都压在同一个组件上——**KV Cache 的生命周期管理**。

- TTFT 的杀手锏「前缀命中跳过 prefill」，前提是 KV Cache 能按 token 前缀索引、能共享；
- 吞吐的大头「3FS 复用、显存驻满」，前提是 KV Cache 能逐出、能落盘、能恢复；
- 推测解码的「验证后回滚」，要求 KV Cache 支持「按层精确截断到第 N 个 token」。

这就是为什么 [第 06 章](06-kvcache.md) 是全书技术密度最高的一章，也是 DeepInfer 未开源的两个组件恰好包括「KV cache 管理」的原因——它是整套系统的状态中枢，所有高级能力的地基。
