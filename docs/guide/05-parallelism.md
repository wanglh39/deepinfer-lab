# 05 并行策略：Attention DP + Wide-EP + EPLB

671B 的模型，权重 FP8 要 671 GB，加上 KV Cache 和临时激活，任何单卡（H800 显存 141 GB）都放不下，必须切到多卡。**怎么切**就是并行策略。本章的核心结论先给出来：prefill 和 decode 的最优切法完全不同，而且 DeepInfer 在**同一个模型的不同层上混搭了两种并行**——注意力层用数据并行（DP），MoE 层用专家并行（EP）。这个混搭是本章要讲透的东西。

## 1. 先建立词汇：切模型有哪几种切法

并行的教科书分类，按「切的是什么」分三种。第一次接触不必怕，记住直觉就够了：

**数据并行（DP，Data Parallel）**：每张卡放**完整的模型**，各自处理**不同的数据**。训练里最常见——每卡算自己那批数据的梯度，再同步。卡间通信只发生在同步点。放在推理里：每张卡服务不同的一组请求。

**张量并行（TP，Tensor Parallel）**：把**单个矩阵**切开——比如一个大权重矩阵按列切成两半，两张卡各算一半，结果再拼起来（每层要一次 all-reduce 通信）。单卡放不下的大层靠它装下，代价是**每层每步都要通信**。

**专家并行（EP，Expert Parallel）**：MoE 专用的切法。MoE 有几百个独立的「专家」（小网络），token 按路由表被发给「持有目标专家的卡」去算，算完发回来。天然按**模块边界**切，通信发生在 dispatch/combine（[第 04 章](04-kernels.md) DeepEP）。

还有一个流水并行（PP，按层切），DeepInfer 的集群里用得不多，本文略过。

现在可以问本章真正的问题了：**decode 的注意力为什么选 DP？MoE 为什么选 EP 而且开到 64~128 卡这么宽？**

## 2. decode 注意力：DP 的完美场景

decode 每步对一条请求做的事：读它自己的全部 KV Cache，算 1 个新 token 对全部历史的注意力。注意这个操作的**数据范围**——KV 是这条请求私有的，新 token 也是这条请求私有的。

这意味着：**只要一条请求从头到尾住在同一张卡上，decode 的注意力就是纯本地计算，卡间零通信。** 这正是 Attention DP 的安排：每个 D 节点的每张卡独立服务一组完整请求（所有层、所有头都在本地），请求进卡后不再搬家。

反面对照是 TP：如果为装下模型把注意力按头切到 8 张卡，每层每步都要一次 all-reduce。decode 的完整 step 才 10~20 ms，一次跨卡 all-reduce（NVLink 上几百微秒、跨机 RDMA 几毫秒）乘上 60 层，TPOT 直接翻倍还多——**decode 的毫秒预算里塞不下每层通信**。而 prefill 一个 step 几百毫秒，摊得起。

DP 的扩展性也最干净：卡数翻倍 = 可服务的并发请求数翻倍，卡间注意力零通信，没有协调成本。代价是每张卡要有完整的注意力权重——注意力层参数不大（相对 MoE），装得起。

## 3. MoE：Wide-EP（64~128 卡）

注意力之外的参数大头在 MoE 层：几百个专家，每个专家是个两层 MLP。这些专家**天然是可切的独立模块**——把 256 个专家分到 64 张卡（每卡 4 个），token 按路由表 dispatch 到持有目标专家的卡。这就是 EP。

「宽」（64~128 卡）的含义和收益值得算一下直觉账。EP 的通信量约等于「token 数 × top-k × hidden 维度」，通信的**固定延迟**是常量。prefill 一次发 10000 个 token，每个 all-to-all 消息都很大，延迟占比微不足道；token 数还保证每个专家分到的 batch 足够大——**分母（每卡专家数）越小、分子（总 token）越大，单专家 batch 越肥**，DeepGEMM 的「分块满血」模式（[第 04 章](04-kernels.md)）才能吃满算力。所以 P 节点敢开到 EP64~128。

decode 反过来：每卡每步只发一两个 token，EP 的通信变成「高频小消息」，固定延迟占比反噬 TPOT。所以 D 节点的 MoE 用**小范围 EP + 专家复制**——把热门专家的权重在多卡放副本，路由就近命中，通信尽量不出卡。

## 4. 组合拳：一张卡的双重身份

现在把第 2、3 节拼起来，得到 DeepInfer 集群最独特的结构——**同一个模型，按层类型混搭两种并行**：

```text
注意力层：  每卡是 DP 成员  —— 服务本地请求的完整注意力，零通信
MoE 层：    每卡是 EP 成员  —— 接收全局路由来的 token，算本地专家
```

一次 decode step 里，一张卡的经历是这样的：先用**本地**请求的 token 算注意力（DP 身份，无通信）；进入 MoE 层，把本地 token 按路由表发给各专家所在的卡（EP 身份，all-to-all），同时接收别的卡发来的、目标专家在本卡的 token，算完再发回去；下一层回到注意力（DP 身份）。注意力段完全不通信、MoE 段集中通信——**每层的并行策略贴着该层的负载特性选**，而不是全局统一一种切法。

这解释了为什么这个组合高效：两种并行各自的缺点被对方的场景回避了——DP 的「权重复制」浪费发生在注意力层（参数小，浪费得起），EP 的「通信重」发生在 MoE 层（prefill 侧 token 多摊得薄，decode 侧用复制绕开）。第 03 章 P/D 分离说「两类节点按各自瓶颈调优」，落到并行维度就是本章这套混搭。

## 5. EPLB：专家放置的动态均衡

EP 有一个内生问题：**路由是数据驱动的**。哪段时间流量偏代码，「代码专家」被路由的频率可能是冷门专家的几倍。放置是静态的（每卡 4 个专家），负载却是流动的——热专家所在的卡排队，冷专家的卡闲着，整集群吞吐被最热的卡卡住（木桶效应）。

EPLB（Expert Parallelism Load Balancer）闭环解决：

```mermaid
timeline
    title EPLB 的生命周期
    采集 : 持续统计各专家的真实 token 流量
    决策 : 计算新放置（过热专家复制到多卡）
    迁移 : 专家权重搬运（选低峰期）
    切换 : 新请求按新表路由，旧请求走完旧路径
```

两个细节值得注意。**专家是可复制的**：一个热门专家可以在 4 张卡各放一份，路由层把发给它的 token 在副本间均衡分发——缓解热点比搬家温和得多。**切换是无扰的**：重排期间新请求立即用新放置表，在跑的请求沿着旧路径走完——不存在「一半 token 在旧卡、一半在新卡」的撕裂窗口。

!!! note "未开源组件之二"

    DeepInfer 未随仓发布负载均衡组件（与 KV cache 管理并列的两个空缺，见
    [第 03 章](03-architecture.md)）。可以推测原因：均衡策略与集群拓扑、
    专家容量配置、真实流量画像深度耦合，剥离出「通用正确」版本的
    工程成本高于收益。

## 6. miniflow 的教学对应

miniflow 单进程跑 CPU，物理并行不存在，但模型**结构的可并行性**全部保留——你能在 config 里看到 DeepSeek 系模型「可被按层混搭切分」的物质基础：

| DeepInfer 并行概念 | miniflow 结构 | 位置 |
|---|---|---|
| MLA/GQA 压 KV | `num_kv_heads=2 < num_attention_heads=4` 的 GQA | `miniflow/config.py` |
| MoE top-k 路由 | 逐 token 的专家路由 + 加权求和 | `miniflow/model/moe.py` |
| 专家容量/过载丢弃 | top-k 之外的专家不激活（无容量丢弃，简化） | `miniflow/model/moe.py` |
| SWA 稀疏层 | 滑动窗口注意力（窗口外位置不参与） | `miniflow/model/layers.py` |
| dense/MoE 层混排 | transformer.py 按层类型异构组装 | `miniflow/model/transformer.py` |

最值得看的观察点：**哪些层是 MoE、哪些层带 SWA，全部写在 config 里**。模型结构的异构性（dense/MoE、全注意力/SWA 混排）正是并行策略「按层混搭」的前提——并行不是部署阶段强加的，是模型设计阶段就预埋的自由度。
