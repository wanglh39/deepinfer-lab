# 02 三大设计目标

第 01 章说过，推理服务被三个指标拉扯：TTFT、TPOT、吞吐。本章把它们升级为三个**设计目标**——低延迟、高吞吐（= 低成本）、确定性——并讲清楚每个目标真正的难点在哪、手段为什么有效、以及它们为什么互相打架。

DeepInfer 的每个子系统都能挂回这三个目标；以后你看到任何一段代码感到「为什么这么绕」时，回到这章找它服务的目标。反过来说，读任何推理框架（不只 DeepInfer）的设计文档，先问「它在服务哪个目标、牺牲了哪个目标」，就能迅速定位它在整个设计空间里的坐标。

读完本章，你应该能不假思索地回答这些问题：

- TTFT 和 TPOT 分别由哪段计算决定？为什么优化手段几乎没有交集？
- 为什么大 batch 几乎总是划算的？它的两个前提是什么？
- 吞吐数字的三个「水分维度」是什么？
- 确定性为什么不是天然成立的？两个泄漏源是什么？
- 三个目标的最强手段为什么都压在 KV Cache 管理上？

本章路线：先从「人的体感」出发把延迟指标落到数字（目标一），再算摊销和成本的账（目标二），然后拆确定性的泄漏源（目标三），最后用 SLO 把三个目标的冲突仲裁掉，并给出「目标→机制」的全书映射表。三笔核心的账（prefill 时长、组批摊销、成本链）都配了完整的推导卡，值得手抄。

## 目标一：低延迟

### 先看人：延迟的体感地图

在谈机器之前先谈人，因为 SLO 的数字最终是从人的体感倒推的。

人对「等待」的心理有一条著名的曲线（约 0.1 秒 / 1 秒 / 10 秒三档）：0.1 秒内的响应感觉是「即时」的——界面像是直接连着手；1 秒左右是「对话」节奏——注意力不断，但能察觉到换手了；10 秒是「任务」节奏——人会切走干别的，回来时耐心已经折损。

把这条曲线对到 LLM 服务上，得到四类典型产品的延迟预算表（SLO 制定的出发点）：

| 体感档位 | 对应指标 | 大致数字 | 对应体验 |
|---|---|---|---|
| 即时（0.1 s） | — | 达不到也不必要 | 打字机首字 |
| 对话（1 s） | TTFT | < 1~2 s | 「反应快」 |
| 流畅 | TPOT | < 50 ms | 打字匀速不卡 |
| 阅读节奏 | TPOT | < 25 ms | 内容涌现感 |
| 任务（10 s） | 整请求 | 看长度 | 可后台化 |

两个推论。第一，**TTFT 和 TPOT 是两种完全不同的等待**：TTFT 是「它听懂我说话了吗」的焦虑，TPOT 是「它说话利不利索」的烦躁。前者用户上限约 2 秒，后者约 100 ms 就开始烦。第二，**总时延 = TTFT + TPOT × (输出长度 - 1)**，对 500 token 的典型回答，TPOT 每恶化 10 ms 总时延多 5 秒——长回答的体验大头在 TPOT，短问答的大头在 TTFT。这解释了为什么两边的优化要分开做。

第三条推论平时没人提但值得想想：**预算表随产品演化移动**。语音对话产品（实时通话里的 AI）要求端到端语音往返 < 500 ms，留给 LLM 的预算被压缩到 ~200 ms——TTFT 和 TPOT 同时被砍到毫秒级极端，逼出「边生成边合成语音」的流式管线（每个词一出来就转语音，不等句子）；反过来，后台 agent 的预算宽松到秒级。**同一套引擎技术，在不同产品里服务完全不同的预算结构**——这就是「目标」必须显式化的原因。

### TTFT 由 prefill 决定

收到请求后，引擎要先把整段 prompt 一次性前向完（这步叫 prefill，因为是在为生成「填充」KV Cache），才能吐出第一个 token。

prompt 有 10000 个 token，这就是一次 10000 个位置的大矩阵乘。注意它和 decode 的本质区别：prefill 一次算成百上千个位置，**同一份权重服务 10000 个位置**，算术强度高，是**计算受限**的，GPU 的算力能吃满。

算一笔 prefill 的账（沿用第 01 章的数字，H800：FP8 算力约 1000 TFLOPS，带宽 3.35 TB/s，模型激活参数 37B）：

- 计算量：$10000 \times 74 \text{ GFLOPs} = 740 \text{ TFLOPs}$；
- 按 MFU（Model FLOPs Utilization，算力实际利用率）60% 算，耗时约 $740 / 600 \approx 1.2 \text{ s}$；
- 搬运量：权重 37 GB（全部位置共享）+ 少量 IO，约 11 ms——相比计算时间可以忽略。

看到了：10000 token 的 prompt，光 prefill 就要 1.2 秒左右，而且瓶颈是**算力**。这 1.2 秒是 TTFT 的下限主体（还要加排队和网络）。要压它只有三条路：

1. **少算**：前缀缓存——如果 prompt 前 9000 token 和别的请求共享（同一个 system prompt + 同一个文档），命中部分跳过，只算后面 1000 个（第 06 章）；
2. **快点算**：更高效的 prefill 算子，比如 DeepGEMM 的 FP8 大 GEMM 把 MFU 从 40% 提到 60%+（第 04 章）；
3. **分摊着算**：chunked prefill——把 1.2 秒切成 12 块、每块 100 ms，块间穿插别的请求的 decode（见下）。

注意这三条路的性质完全不同：第一条是「结构性省钱」，第二条是「工程提速」，第三条是「排队调度」。TTFT 优化横跨存储、算子、调度三层——这是它作为设计目标的第一个难点。

### 顺手解剖：MFU 为什么只有 50~60%

上面的账用了「MFU 60%」，这个数字值得展开——峰值算力是纸面值，实打实的损耗有一整条清单：

- **注意力部分**：prefill 里注意力计算占总 FLOPs 的三成左右，它不是规整大 GEMM（序列长度维度的 softmax、mask 混在里面），利用率天然低于 GEMM——FlashMLA 的分块设计就是在救这部分（第 04 章）；
- **小 GEMM 尾巴**：序列切 chunk 后每 chunk 的最后一个分块往往不满（比如 4096 对齐的 kernel 遇到 3000 的尾巴），尾部空转；
- **MoE 分组**：每个专家分到的 token 数不齐，DeepGEMM 的分组 GEMM 要按最坏情况分配资源，负载不满时 SM 空转（第 04 章）；
- **通信空洞**：TP/EP 的 AllReduce/分发期间，算力在等数据（第 05 章）；非重叠的通信每 1% 就是 1% 的 MFU；
- **kernel 间隙**：每个 kernel 启动有微秒级开销，一层十几个 kernel，间隙积少成多——算子融合（写一个大 kernel 替代一串小 kernel）直接消它。

行业现实：LLM prefill 的 MFU 做到 60% 已是一线水平（DeepGEMM 的公开数据在这个量级），40% 是普通水平。**读懂一个系统的 MFU，等于读完它的算子工程成绩单**——这个视角第 04 章会反复用。

### TPOT 由 decode 决定

之后每步只算 1 个位置，第 01 章算过账：带宽受限，芯片在等数据。37 GB 权重读一遍约 11 ms，这是 batch=1 的 TPOT 下限。

TPOT 的优化手段和 TTFT 几乎不重叠：组批摊薄权重读取（第 07 章）、MLA 压缩 KV 搬运量（第 04/06 章）、推测解码一步多 token（第 08 章）、decode 节点堆带宽和显存而不是算力（第 03 章）。

一个计算受限、一个带宽受限——这就是本章最重要的认知：**「低延迟」不是一个目标，是两个目标**。混在一起谈，优化就会互相抵消。

### 两种计算为什么互相伤害

它们不仅手段不交集，混在同一个 GPU 上还会**互相污染**。具体机制：

prefill 的大矩阵乘会占满计算单元和几十毫秒到几百毫秒的整段时间。这段时间里排队的 decode step 干等——正在生成的用户那边，出字直接卡住。卡多久？一个 10000 token 的 prefill 连续跑就是 1.2 秒的「哑火」：TPOT 从 50 ms 瞬间劣化到秒级，用户看着屏幕以为断线了。

反过来，一堆小 decode step（每个 10~50 ms）让刚启动的大矩阵乘频繁让路：SM（流式多处理器，GPU 的计算单元组）刚把 cache 预热、张量核刚排满流水，就被切走去算 decode 的碎活，prefill 的 MFU 掉一截，TTFT 跟着变差。

所以 DeepInfer 的手段从「加速」转向「隔离」：

- **P/D 分离**（[第 03 章](03-architecture.md)）：prefill 和 decode 分别部署到不同节点群，各自按自己的瓶颈调优——prefill 节点堆算力，decode 节点堆显存带宽和容量。物理隔离最彻底，代价是中间要把 prefill 算好的 KV Cache 通过网络搬过去；
- **chunked prefill**（[第 07 章](07-scheduler.md)）：无法分离部署时（单机场景），把一段长 prefill 切成小块，每算一块就插一步 decode，让正在生成的请求不被饿死。代价是这段 prefill 自己变慢（流水被打断 + 额外调度开销），所以它是在 TTFT 和 TPOT 之间按需调权的开关。

用数字感受 chunked 的权衡：10000 token 的 prefill 切成 1000-token 的 10 块，每块约 120 ms。decode 请求的 step 间隔从「偶尔卡 1.2 s」变成「每块后让 120 ms」——TPOT 的 P99 大幅改善；但这段 prefill 总耗时从 1.2 s 涨到约 1.5 s（流水损耗），TTFT 变差 25%。**同样的硬件，同一秒钟，两个指标在拔河**。

### TPOT 的方差：节奏比速度更伤体感

体感地图里有个没展开的维度：**出字的「均匀度」**。两个系统平均 TPOT 都是 60 ms，一个每步严格 60 ms 匀速出字，另一个抖成 20/20/140/20/20/140 的节奏——后者体感明显更差：每 6 步一次 140 ms 的停顿，用户感知为「卡了一下」，尽管平均值相同。

这不是玄学，人对不均匀节奏的负面感知在 HCI（人机交互）研究里有据可查，而且 LLM 场景把它放大了：流式打字机的隐喻让用户把「节奏」当成了「机器的呼吸」，呼吸乱了就是「要断气」。

TPOT 方差的来源，值得列一下（每个都对应后面的设计）：

- **批组成的抖动**：同批请求的 KV 长短不一，step 耗时随批内最长者波动——连续组批让批的构成每步都变，方差天然存在。缓解靠调度器的批稳定化（第 07 章）；
- **偶发 prefill 插入**（单机混跑）：一次插入，几百 ms 的空档——chunked prefill 就是为削平它而生；
- **推测解码的赌性**：猜对 5 个 token 的那步很快，全猜错的那步很慢——步长天生不均匀（第 08 章），这是它换速度的隐形成本；
- **网络分片粒度**：SSE（Server-Sent Events，流式推送协议）的分片如果攒多个 token 才发一次，客户端看到的是「一次蹦几个字」的台阶式节奏。

监控上这意味着**只盯 TPOT 均值会漏掉节奏问题**：P99 TPOT 能抓到尾部，但「方差大而尾部不极端」的情形要靠 ITL 的标准差或「连续 N 步 > 100 ms 的次数」这类指标。DeepInfer 的 SLO 直接定在 P99 ITL 上，用分位数兜住节奏的坏情况——指标设计里藏着对体感的理解。

### 流式分片：最后一段管道

顺着网络这层把流式链路说完。token 从 GPU 到屏幕的最后一程：

```text
引擎（每 ~30ms 一个 token）
  → 流式帧（SSE/WebSocket，含调度延迟）
    → 服务端缓冲（可能攒批）
      → 公网（RTT + 抖动）
        → 客户端缓冲（前端框架的渲染节奏）
          → 屏幕
```

任何一层攒批都会把匀速流变成台阶流。服务端常见的坑是反向代理（nginx 默认缓冲响应）把流式响应攒成一坨——首 token 到了代理但没到用户，TTFT 监控（引擎侧）好看、体感（客户端侧）稀烂。这正是「测量埋点」一节坚持客户端口径做 SLO 的原因：**SLO 要埋在离用户最近的地方，优化要发生在离指标最远的地方**，两头的错位是流式系统排障的经典迷宫。

前端的处理也有讲究：匀速播放（前端按固定间隔渲染缓冲区里的 token，攒下的按节奏吐）可以隐藏网络抖动，代价是引入固定的显示延迟。聊天产品几乎都这么做——又一个「拿一点延迟换体感稳定」的例子，和 chunked prefill 的哲学一脉相承。

### 容易被忽略的 TTFT 杀手

除了 prefill 本身，还有几个 TTFT 的隐性构成，每个都有专门的设计：

**排队。** 请求到达时如果引擎的批已满，就在等待队列里干等。高峰期排队可以轻松吃掉几百毫秒到几秒，比 prefill 本身还贵。缓解手段是调度器的优先级设计（第 07 章）和集群层面的负载均衡（第 03 章）。

**结构化输出的编译。** 如果用户要求输出匹配一个复杂的 JSON Schema，引擎要把 schema 编译成语法自动机（[第 10 章](10-structured.md)），复杂 schema 的编译可能要几百毫秒——如果这段编译阻塞在第一个 token 之前，用户就在界面上干等。DeepInfer 的做法是把编译放到专用的机器上异步执行，decode 侧拿到编译结果之前先按「无约束」跑着，拿到后才开始施加约束。这个「先跑着再约束」的设计有个精妙的细节：前几个 token 通常在生成引子或空白，不受 schema 约束，所以无约束地先跑几乎不产生废功——设计者对「编译慢」的让步和「输出前缀无害」的观察咬合在了一起。

**冷启动。** 请求的 KV 如果被逐出到 3FS（第 06 章），服务它要先拉回 KV——这是一次网络 IO，量级几十毫秒到几百毫秒。前缀缓存命中的收益能不能兑现，取决于「取回」这步的设计。

所以把 TTFT 拆到底，它是四段之和：

```text
TTFT = 排队等待 + prefill 计算（或前缀命中后的部分计算）
     + 约束编译（如有，可异步化）
     + KV 取回（如被逐出）
```

每一段都有专门的设计压它。以后你看到任何一个「TTFT 优化」的新闻，先对号入座它在压哪一段——大部分宣称只压 prefill 计算那一段，而生产里往往排队和取回才是大头。

### 测量：TTFT/TPOT 的时间戳埋在哪

谈了这么多 TTFT/TPOT，一个工程细节值得专门说：**测量的位置**。位置不同，数字含义完全不同。

一条流式请求的生命周期里，可以打时间戳的点至少有五个：

```text
t0 客户端发出
t1 网关收到（鉴权/限流后）
t2 引擎收到（入队完成）
t3 首个 token 生成完（引擎侧）
t4 首个 token 到达客户端
```

- 客户端口径的 TTFT 是 $t4 - t0$：含网络往返、网关处理，是「用户体感的真值」，但混入了非引擎因素，不适合衡量引擎本身；
- 引擎口径是 $t3 - t2$：纯引擎行为，做回归对比用这个；
- 服务口径是 $t4 - t1$ 或 $t4 - t0$：对外承诺 SLO 用这个。

一个常见事故：引擎团队优化了三周，引擎口径 TTFT 从 900 ms 降到 500 ms，看 SLO 监控（服务口径）却纹丝不动——因为该集群的 TTFT 大头在网关排队和公网 RTT。**优化之前先确认瓶颈在你看得到的区段里**，这句话值一次 three-week sprint。

TPOT 同理：分母要用「token 间隔数」而不是 token 数（500 个 token 只有 499 个间隔）；而且要按流式分片对齐（一个网络分片可能装 2 个 token，客户端看到的是「一次蹦 2 个字」的节奏，体感 TPOT 是分片间隔×2）。这些细节决定了监控曲线能不能和用户投诉对得上。

### Goodput：吞吐的 SLO 化

把延迟和吞吐彻底合到一个指标里，是近年系统论文的一个重要提议（SGLang 系的工作）：**Goodput = 每秒产出的、SLO 达标的 token 数**。

Raw throughput 数所有 token，不管它们来得多迟；Goodput 只数「按时到达」的。压测时把负载从低往高扫，会出现三个区域：

- 低负载区：全部请求 SLO 达标，Goodput = throughput，一起涨；
- 退化区：throughput 还在涨，但部分请求超 SLO，Goodput 涨得慢了——**多出来的吞吐是拿延迟换的脏吞吐**；
- 崩溃区：负载再高，排队雪崩（排队时间长 → 并发积压 → KV 显存耗尽 → 换页/抢占 → 更慢 → 更多积压），Goodput 掉头向下，throughput 也在掉。

**Goodput 的峰值点就是这台机器「健康服务能力」的上限**，比 throughput 峰值（通常出现在崩溃区边缘）科学得多。容量规划按 Goodput 峰值留 buffer，而不是按 throughput 峰值顶格——这就是第 11 章部署配方的容量观。

DeepInfer 的 SLO 导向调度（见下节）本质就是在让「负载-Goodput 曲线」的退化区右移：同样的负载下，超时请求更少。你以后看到「我们的系统支持 10×并发」之类的宣称，心里换算的第一件事就是：这是 Goodput 意义上的 10×，还是吞吐数字意义上的 10×？


## 目标二：高吞吐

同样的硬件，单位时间产出多少 token。这项指标直接换算成成本：8 块 GPU 的集群，吞吐翻倍等于每个 token 的成本减半。

先把定义抠严实一点，因为「吞吐」这个词有口径问题。

### 吞吐的口径

**产出 token 数怎么数？** 行业里有两个口径：只数 decode 产出的（生成 token 数），和把 prefill 处理的输入 token 也算上的（总 token 数）。两者能差出一个数量级（重 prefill 流量下输入远大于输出）。对比任何两个系统的吞吐数字前，先统一口径。

**在哪个层面数？** 单卡、单机、单副本、集群？多副本的集群吞吐有负载均衡损耗，单副本数字不能线性外推。

**什么流量下的数字？** 这是最重要的：prefill-heavy（长文档问答，输入 10000、输出 200）和 decode-heavy（闲聊，输入 50、输出 800）的流量画像完全不同，同一集群两种流量的吞吐能差数倍。没有流量画像的吞吐数字基本没有意义。

本书后面说「吞吐」，默认口径是：**单副本、decode 产出 token、给定流量画像下**。记住这三个限定词，你就比大部分吞吐对比文章严谨了。

### 延迟和吞吐在哪里打架

第 01 章说过组批是带宽矛盾的解药，但组批有一个副作用：**batch 越大，单条请求的 TPOT 越差**。同一块 GPU 的带宽是固定的，batch=64 时 64 条请求的 KV Cache 读取分抢同一条总线，每条请求等到的数据都晚了一些。

但关键在于恶化的**速度**：TPOT 并不随 batch 线性变差。把这笔账完整算一遍（这是本章最重要的一笔账，值得手抄）。

设权重每步要读 $W$ = 37 GB，每条请求的 KV 平均 $K$ = 1 GB，batch 为 $B$。三个量按顺序算：

每步总搬运量（权重读一遍，每条请求的 KV 各读各的）：

$$
\text{搬运量}(B) = W + B \times K
$$

每步产出 $B$ 个 token（batch 里每条请求各出 1 个）。于是**单 token 摊销搬运量**：

$$
\text{摊销}(B) = \frac{W + BK}{B} = \frac{W}{B} + K
$$

这个形式揭示了结构：第一项 $\frac{W}{B}$ 随 batch 摊薄，第二项 $K$ 是**摊不掉的底价**——KV 是每条请求私有的，跟谁拼批都省不掉。TPOT 粗估为 $\text{摊销}(B) / 3.35 \text{ TB/s}$。代几个数：

| $B$ | 搬运量 | 单 token 摊销 | 相对 $B=1$ | TPOT |
|---|---|---|---|---|
| 1 | 38 GB | 38 GB | 1× | ~11 ms |
| 8 | 45 GB | 5.6 GB | 6.8× 好 | ~13 ms |
| 32 | 69 GB | 2.2 GB | 17× 好 | ~21 ms |
| 64 | 101 GB | 1.6 GB | 24× 好 | ~30 ms |
| 128 | 165 GB | 1.3 GB | 29× 好 | ~49 ms |

看清楚两条曲线的形状：

- **单 token 成本**（吞吐侧）：从 $B=1$ 到 8 立刻降到 1/6.8，到 64 降到 1/24，到 128 只有 1/29——边际收益递减，因为 $\frac{W}{B}$ 项在缩小而 $K$ 项恒定。极限是 $K$ 本身：**KV Cache 是摊不掉的底价**。
- **TPOT**（延迟侧）：从 11 ms 涨到 30 ms（$B=64$），恶化不到 3 倍。

所以吞吐随 batch 增长远快于 TPOT 恶化，大 batch 几乎总是划算的——**前提是两个**：你有那么多请求可拼（流量密度），显存放得下这么多并发请求的 KV Cache（容量）。这两个前提分别是调度器（第 07 章）和分页 KV（第 06 章）的战场。

这张表还预告了后面好几章的动机：

- **MLA 压缩 $K$**（第 04/06 章）：$K$ 从 1 GB 压到 0.2 GB，TPOT 恒定项直接砍 80%，同 batch 下 TPOT 大幅改善——压缩 KV 就是在压这张表的最后一列；
- **EPLB 让并发均匀**（第 05 章）：64 条请求如果全堆在一块卡上而别的卡空着，等于 $B$ 很大但别的卡 $B=0$，集群总吞吐次优；
- **3FS 换页扩容**（第 06 章）：显存装不下 $B=64$ 的 KV 时，把冷请求的 KV 挪出去，等效于显存变相扩大。

### DeepInfer 提吞吐的三个手段

**手段一：E/P/D 分离部署。** prefill 节点专心拼大 batch 吃满算力，decode 节点把 KV Cache 驻满、带宽跑满。两类负载各自趋近最优，不再互相污染。

上一节表格里省略的一点：集群的「有效 batch」其实由最慢的环节决定。混跑时 prefill 长任务插入，decode 的有效 batch 在那 1.2 秒里等于零——这就是混跑的吞吐暗损。分离后 decode 节点的 batch 曲线平滑，均值就是稳态。

**手段二：前缀缓存 + 3FS 持久化**（[第 06 章](06-kvcache.md)）。大量流量共享同一段 system prompt。这段的 KV Cache 只需算一次，之后所有请求直接复用——省下的 prefill 算力就是白捡的吞吐。

量化一下这个「白捡」有多肥：假设 system prompt 3000 token，日流量 100 万次请求。没有前缀缓存，这 3000 token 每次都重新 prefill：$10^6 \times 3000 = 3 \times 10^9$ token 的 prefill 计算。有前缀缓存且命中，这部分计算归零——按 prefill 算力 600 TFLOPS 折算，约 $3 \times 10^9 \times 74000 / 6 \times 10^{14} \approx 370$ GPU·秒/天，单是 system prompt 一项。真实的 agent 流量里共享前缀更长（整个工作流的人设+工具说明），命中率更高，收益再乘一个系数。

3FS 更进一步：把 KV 落到分布式文件系统，跨请求、跨时间段复用（TTL 3~7 天），连「不同时刻到达的请求」都能共享。上午 10 点算好的文档 KV，下午 3 点的新请求接着用——**吞吐收益从「同时刻并发」扩展到「时间轴上的所有流量」**。

**手段三：推测解码**（[第 08 章](08-speculative.md)）。DSpark 的生产数据是变长验证带来 +4~7% 吞吐。听起来不大，但注意它的性质：**纯软件优化换来等效扩容**——不加一台机器，4~7% 的服务成本就没了。在百万 token 服务的规模下，这就是一笔大钱。

为什么只有 4~7% 而不是理论上的几十？因为验证有开销（多算的位置）、猜错有回滚（KV 截断重算）、而且收益随 batch 增大被稀释——batch=64 时算力已经比较忙，闲算力少了，猜的空间就小。**推测解码是「算力闲时」的套利，组批已经把闲时用掉一部分**。这两个手段的组合是「先组批、再用推测解码吃掉剩余闲时」，第 08 章会算这条边界。

### 提醒：吞吐数字的水分

看到一个「XX tokens/s」的宣称，要能问出三个问题：

1. **什么模型**：参数量决定每 token 的搬运量，671B 和 7B 的数字差几十倍；
2. **什么长度分布**：prefill 重还是 decode 重，吞吐能差数倍（口径一节的三个限定词）；
3. **什么并发**：batch 拼到多大、流量是否足够密。低负载跑出来的「单请求延迟」和高压测出来的「满载吞吐」是两个极端，都不能代表真实服务。

DeepInfer 内部用一个拟合的成本模型 cost(q, c)（q 为 chunk 大小、c 为并发）量化「prefill 和 decode 混跑一台机器」的损失，用数据决定分还是混，而不是拍脑袋。这个思路值得抄：**任何「隔离 vs 共享」的架构决策，都应该有个成本模型兜底**——隔离有网络搬运的代价，共享有互相污染的代价，哪个贵用数据说话（第 03 章会展开这个模型的用法）。

### 一个 token 卖多少钱：成本的完整解剖

把「吞吐 = 成本」这句话做实。从 GPU 租金一路推到 API 价目表上的每百万 token 价格，这条推导链值得每个做推理的人亲手走一遍。

**第一段：硬件时薪。** 一台 8 卡 H800 服务器，市场租金约 $20~$30/小时（含电和机房，粗算取 $25）。一秒钟的租金：$25/3600 \approx 0.7$ 美分。

**第二段：有效产出。** 假设这台机器满载 decode 吞吐约 4000 token/s（第 01 章 batch=64 的账打些折扣，再加上 prefill 占比、SLO 约束下的保守 batch，这是生产现实量级）。每秒有效利用还要打折：真实服务有流量波动，平均利用率能到 70% 已属优秀——有效吞吐 $4000 \times 0.7 \approx 2800$ token/s。

**第三段：每 token 硬件成本。**

$$
\frac{0.7 \text{ 美分/s}}{2800 \text{ token/s}} \approx 0.00025 \text{ 美分/token} = 0.25 \text{ 美元/百万 token}
$$

**第四段：到价目表还有两倍。** 硬件成本只是地基：研发摊销（写 DeepInfer 这种引擎的工程师时薪）、流量获取、免费额度、故障冗余（灾备集群平时闲着，第 11 章）、计费系统本身……行业经验毛利要翻 2~4 倍，落到价目表上就是 $0.5~$1/百万 token 的量级——对照各家 API 的实际定价（补贴战打出来的价格另当别论），这条链是通的。

走完这条链，「吞吐翻倍 = 成本减半」就不再是口号，而是每一步的乘数：MFU 提升 10%、前缀缓存省 20% prefill、推测解码 +5%……全部直接乘进分子分母。**推理系统的每一个优化，最终都兑现成价目表上的小数点**——这就是 DeepInfer 团队为什么值得在「几个百分点」上投入数月的原因。

还有一个镜像视角：**这条链也解释了为什么大推理集群动辄千卡**。目标服务 1 亿日活、人均日对话 20 轮、每轮 1000 token：$10^8 \times 20 \times 1000 = 2 \times 10^{12}$ token/天 ≈ 2300 万 token/s 的持续产出——按单机 2800 token/s 算需要 8000+ 台机器（峰值再乘 2~3）。这就是头部 AI 公司推理资本开支的算术。

### 缓存命中率的经济学

前缀缓存号称「白捡的吞吐」，但「捡多少」由命中率决定，而命中率有自己的结构规律——值得单独算一节。

流量里的前缀分布近似 **Zipf 律**（长尾分布的典型形态：少数前缀出现极多次，大量前缀各出现一两次）。system prompt 是头部（一条被引用百万次），用户各自的开场白是尾部（各出现一次）。命中率的构成天然是「头部贡献大、尾部几乎零」：

```text
命中率 ≈ Σ(被缓存前缀的出现次数) / Σ(所有前缀的出现次数)

例：前缀出现次数分布 [100000, 5000, 500, 100, 50, 20, ×1×10000 条]
    缓存全部 → 命中率 ≈ 105670/205670 ≈ 51%
    只缓存 Top-3（容量受限）→ 命中率 ≈ 105500/205670 ≈ 51%
    ——长尾的一万条「×1」前缀缓存与否，只差 0.1%！
```

结论一：**缓存的边际收益集中在头部，容量不用大**。缓存 Top 前缀的 3 条就拿到 51% 命中率，扩容到缓存全部也才 51.1%——「缓存该多大」的答案是「小而准」，这直接影响了第 06 章 KV 块池的容量预算设计。

结论二：**命中率管理 = 头部识别 + 逐出保头**。头部会漂移（新闻周期、产品改版换 system prompt），逐出策略要快速识别新头、淘汰旧头——LRU（最近最少使用）在漂移下反应慢，LFU（最常使用）惰性强，生产常用带衰减的混合策略。3FS 的 TTL 3~7 天就是给「头部自然换血」留的时间窗。

结论三：**换出显存的收益有上限，但跨时间的收益没有**。同一时刻并发里的共享（RadixAttention）受限于「同时在线的请求碰巧同前缀」；3FS 把复用窗口拉长到天级，同一 system prompt 昨天算的今天还能用——命中率的分母从「当前并发」变成「TTL 内全部流量」，同样的 Zipf 头部被重复利用千百次。这就是 3FS 值得造一套分布式文件系统的经济学。

（这套算法在 miniflow 里有简化版：`examples/demo_prefix_cache.py` 可以注入 Zipf 分布的前缀流量，观察命中率随缓存容量、TTL 的变化曲线——比你读这十遍更有手感。）

### 压测方法论：怎么读一张 benchmark 图

最后一个吞吐相关的话题：怎么正确地测。不是为了发论文，是为了回答「我的服务在什么负载下会崩、崩之前长什么样」。

正确姿势是**负载扫描**：固定请求的长度分布画像，把到达率从低到高扫过去，每个点记录 P99 TTFT、P99 TPOT、吞吐、Goodput 四条曲线。健康的系统会画出三个阶段（Goodput 一节的描述），要看的转折点有两个：

- **Goodput 峰值点**：健康服务能力的上限，容量规划以它为锚；
- **崩溃点**：比峰值再高一点的到达率，队列雪崩开始——**生产负载永远不要贴近它**，因为真实流量的突发（秒级到达率可以是均值的数倍）会瞬间捅穿。

错误姿势是单点测试：「我们测了并发 256，P99 TPOT 80 ms」——这句话什么都没说：并发 256 是稳定状态还是过载瞬间？到达率是多少？长度分布是什么？单点数字没法回答「加到 300 并发会发生什么」。

另一个易错点：**压测流量要用生产画像，不要用均匀分布**。均匀生成的请求长度（比如都是 512 in / 512 out）会让缓存命中、抢占、尾部浪费都失真——真实的长度是重尾分布（多数短、少数极长），恰恰是长尾请求触发调度器的全部边界逻辑。miniflow 的压测脚本（`examples/` 下的 demo 都带随机长度参数）用了简单的重尾分布，就是为了让这些边界行为能被观察到。

## 目标三：确定性与可控性

前两个目标是所有框架共有的，这一个最能区分「跑 demo」和「跑生产」。它说的是：**同一条请求，输出只取决于（输入, 种子），与它恰好在哪个 batch 里、邻居是谁、服务器负载多高，全都无关。**

这个性质有个名字：**batch-invariance**（批不变性）。它听起来理所当然，实际是推理框架里最容易被悄悄破坏的性质。

### 为什么「默认做不到」

初学者通常以为这是天然成立的——毕竟模型权重是固定的。但有两个隐蔽的泄漏源。

**泄漏源一：浮点加法不满足结合律。**

$(a+b)+c \neq a+(b+c)$，误差在浮点下不同。用一个你可以在 Python 里立刻验证的例子：

```python
>>> (0.1 + 0.2) + 0.3
0.6000000000000001
>>> 0.1 + (0.2 + 0.3)
0.6000000000000001   # 这个恰好相等
>>> (1e16 + 1) + 1   # 但大数下必炸
10000000000000000.0  # 1 被吞了
>>> 1e16 + (1 + 1)
10000000000000002.0  # 先加小的就保住了
```

大数吃小数、顺序定生死。框架为了效率会把同批多条请求的张量拼在一起做 reduction（比如 softmax 的分母求和、MoE 的专家聚合）——批里多了谁、顺序怎么排，都会改变求和的运算顺序，进而改变每一位低有效数字。

单独看，一个 ULP（unit in the last place，最低位）的误差无伤大雅。但这个误差会**乘上后面几十层的放大**：注意力分布差一点 → 采样的 logits 排序翻转 → 选中不同的 token → 后续生成完全分岔。50 层后，「差一点」就是「差一个故事」。这就是为什么浮点的非确定性在 LLM 推理里不是学术洁癖，而是实际发生的输出分岔。

**泄漏源二：随机数流是全局的。**

采样要从分布里抽随机数。如果全进程共享一条随机数流（很多框架的默认实现就是全局一个 RNG），批里邻居请求先抽走了几个数，我的随机数就变了——「和我拼批的请求是什么」影响了我抽到什么。

这个泄漏的隐蔽之处在于它**平时无症状**：单请求测试时批里只有自己，怎么跑都一致；一到并发服务，复现就变成玄学。「这个 bug 上周还复现，这周复现不了了」的检查清单里，全局 RNG 应该排在第一位。

### 拆除两个泄漏

所以 batch-invariance 不是「把 seed 固定」就完事，必须**拆除这两个泄漏**：

- **归约顺序与批组成解耦**：每条请求独立归约（不拼批做 reduction，损失一点效率），或用顺序无关的求和方式（比如固定分块树的树形归约——不管输入怎么排，归约树形状固定）。前者简单慢，后者复杂快，第 09 章讲 DeepInfer 的选择；
- **随机流按请求隔离**：每条请求从自己的 (request_id, seed) 派生独立流，邻居抽多少个数都与我无关。

注意这两条都要**拿效率换**：独立归约放弃批并行的 reduction 融合，独立 RNG 放弃全局 RNG 的流水线复用。确定性是设计目标，不是免费赠品——这符合本章的主旋律：三个目标互相打架。

### 分布式把问题放大：第三、四个泄漏源

单机上的两个泄漏源拆掉后，上集群又会冒出新的。分布式推理（第 05 章的 TP/EP）引入了两个更隐蔽的：

**泄漏源三：多卡归约的树形顺序。** 张量并行（TP）把一层切开放到多张卡上，每张卡算一部分、最后 AllReduce 合并。AllReduce 的合并顺序取决于「哪张卡先到」——而谁先到取决于当时的网络拥塞和调度。也就是说：**网卡的拥塞状况悄悄参与了数值计算**。同一个请求跑两次，第一次 hop1 卡先到、第二次 hop3 卡先到，浮点求和顺序不同，结果可能分岔。拆除办法是让归约树形状固定（与到达顺序无关的确定性归约），代价是损失「先到先合」的加速。

**泄漏源四：异步流水线的完成时序。** DeepInfer 的引擎是 CPU/GPU 流水线重叠的（第 07 章）——异步意味着「这一步的计算在下一次运行时可能赶上不同的流水线相位」。如果某处 kernel 的行为依赖输入的内存对齐或抢占状态（比如变长请求的 padding 长度不同导致不同的向量化路径），流水线相位的变化就会传导为数值变化。这类问题的拆除要靠「kernel 行为只由输入内容决定，不由执行环境决定」的纪律——写算子时的军规，不是调度器能事后补的。

四个泄漏源放一起看有个规律：**每一个都藏在「为了效率而共享/合并/重叠」的地方**。批量归约共享运算、全局 RNG 共享随机流、AllReduce 共享网络、流水线共享时间轴——效率来自共享，确定性要求隔离，两者的张力是结构性的。所以确定性设计的艺术不是「全隔离」（那等于放弃性能），而是**隔离到「请求粒度」为止**：请求之间绝对隔离，请求内部随便优化。第 09 章的采样器设计会完整示范这个粒度怎么画。

### 验证确定性：一份可执行的清单

怎么确认你的引擎真的 batch-invariant？光读代码不够（泄漏藏在运行时行为里），要靠构造性的测试。一份实践中有效的清单：

**测试一：双跑对比。** 固定一批请求（建议带长度重尾），跑两遍：第一遍按原顺序全量跑；第二遍打乱顺序、改变并发度分批跑。逐请求、逐 token 比对输出。任何不一致 = 泄漏。

**测试二：邻居注入。** 单请求 A 独跑得到基准输出；然后把 A 和一堆「干扰请求」拼批跑（干扰请求用不同长度、不同采样温度）。A 的输出必须和独跑完全一致——这是对「批组成无关」最直接的攻击。

**测试三：重放对齐。** 录制一段线上流量（含到达时刻），重放时故意改变回放速度（×0.5、×2）。输出必须与线上逐 token 一致——检验「负载无关」。

**测试四：抢占路径。** 构造显存压力让 A 被抢占再恢复，对比「没被抢占的平行宇宙」。抢占路径上最容易发生状态丢失型 bug（少恢复一层 KV、采样流没回卷）。

这四个测试在 miniflow 的 `tests/` 里都有简化版实现，跑一遍只要几秒。有趣的是它们曾经全部失败过——每条测试背后是一次真实的踩坑（踩坑实录见各 lab 章）。**测试不是对理论的装饰，是对伤痕的记忆**。

### 生产为什么需要它

拆除泄漏花的效率，换来的东西在三个生产场景里兑现：

**回归测试。** 改了一版调度器代码，跑一遍测试集，输出必须和改动前一致——否则你分不清「输出变了」是新 bug 还是数值抖动。没有 batch-invariance，每次改调度逻辑都要人肉重审全部输出 diff，测试自动化直接失效。有它，diff 非空就是 bug，一票否决。

**A/B 对比。** 对比两个采样参数（或两个 prompt 版本）的效果，如果输出随批组成漂移，对比结论就是噪声——你测出的是「今天流量长什么样」而不是「参数哪个好」。可控实验的前提是控制变量，而批组成正是推理系统里最活跃的变量。

**分片重放。** 把线上流量切片重放排查问题：切片方式和线上不同（批组成必然不同），没有 batch-invariance 就不能对齐，重放就查不出当时发生了什么。

三个场景的共性：**推理系统自身的开发和运维，依赖输出可复现作为基础设施**。这不是「用户要求每句话都一样」（他们不在乎），而是「系统团队要求出问题能查、改动能验」。把这个目标做扎实，本质是给整个工程体系上保险。

围绕这个目标还有两个相关能力：

- **结构化输出**：Agent 要求输出严格匹配 JSON Schema。靠 prompt 求模型「请输出合法 JSON」是概率性的——99% 合法在生产规模下等于每小时几千次解析失败。把约束做进解码过程（每步只允许从「语法上合法」的 token 里采样，[第 10 章]），合法性从 99% 变成 100%；
- **特殊 token 防注入**：用户输入里字面的控制标记不能改变模型行为分界。模型用特殊 token（如 `<|end|>`）区分角色边界，用户输入里恰好包含这个字符串时，朴素拼接会伪造边界——约束机制要在 token 化层面就保证「用户的话永远是数据、永远不是指令」（[第 11 章]）。

它们共同的底层思路：**把「输出必须满足的约束」做成系统保证，而不是祈祷模型自觉。** 确定性目标的精神从这里延伸：生产系统的质量属性要靠机制兜底，而不是靠概率。

### 案例：三类产品，三种目标组合

把三个目标在不同产品形态里的相对权重走一遍，你会看到「目标组合」怎么决定技术选型：

**案例一：通用聊天产品（网页版助手）。** 用户在屏幕前，TTFT 和 TPOT 都敏感（体感地图的对话档），但对话轮次短、流量巨大。目标组合：延迟优先、吞吐其次（用规模摊）、确定性要求低（用户不在乎复现）。技术选型倾向：P/D 分离保 P99、中等 batch 平衡、不必在确定性上花大钱——这是「体验驱动」的画像。

**案例二：agent 平台（程序化调用）。** 调用方是代码，没有人在屏幕前等单次延迟；但调用链长（50 步串行），链路级尾部被放大，P99 反而最敏感。前缀高度重复（system prompt + 工具描述占输入大头），前缀缓存的收益巨大。目标组合：链路 P99 + 吞吐双高、单次 TTFT 可放。技术选型倾向：RadixAttention 式的前缀复用（SGLang 的甜点区）、确定性采样（A/B 调 agent 参数是刚需）、Goodput 口径的容量规划——这是「工程驱动」的画像，也是为什么 agent 框架偏爱 SGLang、企业服务偏爱确定性。

**案例三：夜间批处理（语料合成、离线标注）。** 没有deadline 压力，唯一指标是每 token 成本。目标组合：吞吐压倒一切。技术选型倾向：batch 拉满到吞吐峰值（不怕崩溃区边缘，反正失败了重跑）、推测解码大胆开（闲算力多）、SLO 只留「别把机器跑挂」的底线——这是「成本驱动」的画像。

**案例四：实时语音对话（AI 电话）。** 端到端语音往返 < 500 ms 的硬约束里，LLLM 只分到 ~200 ms：TTFT 预算被压到几十 ms（等待用户察觉不到停顿），输出必须逐 token 流给语音合成（不能等句子）。目标组合：TTFT 极端优先。技术选型倾向：小模型或投机解码保出字速度、流式 TTS 管线咬合（第 01 章提过的「预算表随产品移动」的极端案例）、放弃长输出（对话轮次短）。这个画像下第 02 章的所有常规权衡全部改写——**设计目标从「优化」变成「在物理极限内塞下」**。

三类画像没有谁对谁错，但**一个引擎想同时服务三类，就要在调度器里实现按租户切换的目标函数**——这就是第 07 章调度器有优先级/预算/配额这些概念的原因。DeepInfer 主要按案例一、二的画像打造（它是自家聊天+API 服务的引擎），案例三的批处理需求通过 API 的低价时段和批量接口承接。

### 新变量：长思考模型重构延迟目标

以上全部讨论隐含一个假设：输出长度是「一段回答」的量级（几百 token）。DeepSeek-R1 这类**推理模型**（reasoning model）打破了这个假设：回答前先吐一条几万 token 的思考链（`<think>...</think>`），总输出长度膨胀一两个数量级。

这对三个目标的冲击值得单独想清楚：

**对 TPOT**：思考链越长，TPOT 的杠杆越大。10 万 token 的思考链，TPOT 从 50 ms 优化到 30 ms，单请求总时延省 2000 秒（半小时）——**长思考把「每 token 快一点」放大成「总时长快一半」**。这就是为什么 R1 发布后各家疯狂堆 decode 速度（推测解码的优先级暴涨）。

**对 TTFT**：用户对「开始思考」的等待容忍度变高了（反正要等很久），但出现了一个新的体感锚点：**思考多久算正常**。10 秒不出结果用户就焦虑「是不是挂了」——于是前端要把思考进度流式展示（「正在思考…已推理 12000 token」）。TTFT 的语义从「首字」变成「进度的持续可见性」，指标设计要跟着变。

**对吞吐**：单请求的 token 数暴涨，同样的到达率下系统总产出涨百倍——容量规划的全部数字重算（Little 定律的 $W$ 变大，并发需求暴涨）。思考链又高度模板化（推理步骤的模式重复），**前缀缓存和推测解码在思考段的命中率/接受率显著高于普通文本**——这是 R1 之后这两个技术地位暴涨的结构性原因。

**对确定性**：长链放大的不只是时延，还有分岔的代价——浮点误差在第 10000 个思考 token 处分岔，后面几万 token 全部不同。batch-invariance 的测试要在长思考流量上重跑，泄漏的暴露概率随链长指数上升。

一个新兴的设计问题留给你思考：思考链要不要压缩存储？思考 token 的 KV 占着显存但生成完就废弃（最终答案不需要回看思考过程）——**「思考 KV 即焚」的调度策略**（生成完立刻释放、不留缓存）能大幅提高 decode 集群的并发容量。这类「内容语义参与调度」的设计，是长思考模型时代的新大陆。

## 三个目标的共同底层：把状态管起来

分别看完三个目标，退后一步会发现一件事：它们的最强手段全都压在同一个组件上——**KV Cache 的生命周期管理**。

- TTFT 的杀手锏「前缀命中跳过 prefill」，前提是 KV Cache 能按 token 前缀索引、能共享；
- 吞吐的大头「3FS 复用、显存驻满」，前提是 KV Cache 能逐出、能落盘、能恢复；
- 确定性的「分片重放对齐」，前提是重放时能把每条请求的 KV 状态精确还原（哪个请求的哪些块、什么版本）；
- 推测解码的「验证后回滚」，要求 KV Cache 支持「按层精确截断到第 N 个 token」。

四项能力——**索引、共享、逐出/恢复、截断**——没有一项是「存个缓存」这么简单。它们要求 KV Cache 像一个正经的存储系统：有地址结构（分页）、有并发控制（引用计数）、有持久层（3FS）、有事务性操作（截断回滚）。每项先给一个 30 秒预览（第 06 章全面展开）：

**索引**：KV 要能按「token 前缀」找到——前缀缓存命中判断的每一步都在查这个索引。数据结构是块表（block table）+ 前缀哈希树：树上一条路径就是一段已知前缀，新请求沿着自己的 token 序列走树，走到分叉点就是「最长公共前缀」，之后的 KV 才需要现算。这个结构决定了「命中」是渐进而非二元的。

**共享**：100 条请求命中同一段 system prompt KV，物理上只有一份，靠引用计数管理归属——最后一条请求走了才能释放。计数错了轻则显存泄漏（块永远放不掉）、重则释放后又被别的请求读到（输出错乱），KV 管理代码里最阴险的 bug 都在这附近。

**逐出/恢复**：显存装不下时，冷数据（刚没被命中的前缀、被抢占的请求）逐出到 3FS；需要时再拉回。这是显存-存储的两级缓存体系，逐出策略（LRU？按 TTL？按引用计数？）直接决定前缀命中率——一个策略选择的差异，能在集群吞吐上放大出两位数的百分比。

**截断**：推测解码验证失败时要回滚到第 N 个 token（第 08 章），KV 要能「精确到层地砍头」。听起来简单，砍的时候要考虑：被砍的块可能正被别的请求共享着（前缀命中过它），砍到共享块要降计数而不是直接释放——事务性操作的复杂性全在边界情形里。

这四项能力在第 06 章逐个变成具体的数据结构和算法；在这里你只需要记住它们的名字和为什么值得占一章的篇幅。

这就是为什么 [第 06 章](06-kvcache.md) 是全书技术密度最高的一章，也是 DeepInfer 未开源的两个组件恰好包括「KV cache 管理」的原因——它是整套系统的状态中枢，所有高级能力的地基。如果本书只能精读一章，读 06。

## DeepInfer 的目标指纹

同一个三目标框架下，不同框架的「优先级指纹」不一样——这解释了为什么它们长成了不同的样子。从公开信息和设计取舍看，DeepInfer 的指纹大致是：

```text
吞吐（成本） > P99 尾延迟 > 平均延迟 > 通用性
```

证据链散落在各章：P/D 物理分离是「吞吐优先于部署简单性」的极端选择（通用框架几乎都不这么做）；3FS 是「吞吐优先于通用性」（专门为一个模型家族造存储）；反过来它的确定性建设（batch-invariance、结构化输出）又是「生产工程性优先」的深投入。把这些取舍连起来读，DeepInfer 的画像清晰：**一家按 token 卖服务、极度在乎单位成本、同时要求工程质量过硬的公司，会造出来的引擎**。

vLLM 的指纹偏「通用性和易用性优先」，SGLang 偏「前端表达力和 agent 场景优先」。指纹无对错，但**读任何框架源码前先认清它的指纹**，能避免大量「它为什么不用 X 方案」的误问——X 方案可能服务的是另一个目标组合。

## 目标打架时的仲裁：SLO

三个目标既然互相拉扯，工程上就要有仲裁机制。仲裁的依据是**SLO**（Service Level Objective，服务等级目标）：给每个目标定量化底线，超线报警，架构决策向 SLO 倾斜。

DeepInfer 线上服务的公开 SLO（载于其技术报告）大致是：

```text
P99 ITL（inter-token latency，即 TPOT）< 100 ms
P99 TTFT 在「几十秒级」以下（长 prompt 场景宽限）
```

这两个数字怎么来的？不是拍脑袋，是**从产品形态倒推**。把三类典型流量的 SLO 摆成一张表，你能看到「产品形态 → 延迟要求 → 架构倾向」的传导链条：

| 流量类型 | 谁在等 | TTFT 要求 | TPOT 要求 | 吞吐地位 | 架构倾向 |
|---|---|---|---|---|---|
| 交互聊天 | 屏幕前的人 | < 2 s | < 100 ms | 中 | P/D 分离、小 batch 高优先 |
| agent 链式调用 | 下游模型/流程 | 秒级可忍 | < 100 ms（链式放大尾部） | 高 | 前缀缓存（同前缀复用）、尾延迟严控 |
| 代码补全 | IDE 里的开发者 | < 500 ms | < 50 ms（体感最挑剔） | 中 | 小 batch、激进投机解码 |
| 批处理（夜间离线） | 没有人 | 无所谓 | 无所谓 | 唯一目标 | batch 拉满、填谷调度 |

注意 agent 那一行的特殊性：单次调用看似宽松，但 50 次串行的链路会把尾部概率放大到 40%（第 01 章 2.5 算过），所以链路级 SLO 倒逼单请求的 P99 反而更严——**SLO 要看调用链的结构，不能只看单请求**。这是「从产品形态倒推」最不显然的一个例子。

于是调度器（第 07 章）拿到的是三色信号：延迟预算快耗尽的请求标红（优先、甚至抢占别人）、还有富余的标黄（可以捎带）、批处理标绿（填谷）。**SLO 不是装饰性文档，它编译成调度器的优先级输入**——这是「目标」到「机制」的最后一公里，第 07 章走完它。

一个值得记住的权衡实例：为了把 P99 TPOT 压在 100 ms 内，DeepInfer 的 decode 侧宁可把 batch 控制在吞吐最优值以下（牺牲平均吞吐百分之十几），因为 P99 的尖刺几乎全部来自「batch 过大 + 偶发长请求」的组合。**P99 是拿平均值的钱买的**——延迟分位数经济学，第 11 章的容量规划还会再遇到它。

### SLO 定得不好会怎样

SLO 定错的代价值得专门警示，因为错误模式很固定：

**定太松**：产品侧长期「能用但不爽」，竞品上线同配置快一倍，用户无声流失——SLO 是体验的代理指标，代理失真就是慢性失血。

**定太紧**：为了 50 ms 的 P99 TPOT 把 batch 压到 16，吞吐掉一半，成本翻倍——而用户对 50 ms 和 80 ms 的 TPOT 根本无感。**在用户感知不到的地方花 GPU 预算，是 SLO 的过度医疗**。

**只定平均值**：P50 好看，P99 烂穿，agent 链路用户（正是付费最多的一批）体验最差——平均值的坟墓里埋的全是长尾。

正确的定法回到本章第一节的体感地图：**在每个「用户真的在乎」的档位上卡 P99，其余的地方放行**。这需要流量画像（哪类用户、什么调用链）和体感研究的输入，是系统工程和产品工程的交叉地带——推理团队里专门有人盯这个，不是拿模板抄的。

## 工程落点：三个目标住在代码库的哪里

最后一个视角：从设计语言切到源码语言。打开任何一个推理框架的仓库，三个目标分别对应哪些模块？这张地图能让你读 DeepInfer（或 vLLM/SGLang）源码时不迷路：

| 目标 | 典型模块 | 识别特征 |
|---|---|---|
| TTFT/TPOT | 调度器、请求队列 | 主循环 + 每 step 重构 batch 的代码 |
| TTFT | 前缀缓存/块管理器 | 带前缀哈希、引用计数的 KV 分配器 |
| 吞吐 | 组批策略、并发上限配置 | batch size、KV pool 大小的常量与自适应逻辑 |
| 吞吐 | 并行与通信 | TP/EP 的切分与 collective 调用 |
| 确定性 | 采样器 | seed 派生、按请求的 RNG 状态 |
| 确定性 | 归约实现 | kernel 内的求和顺序（藏在最深处） |

两个阅读技巧。**第一，从主循环开始读**：任何引擎都有个 `while True` 的 step 循环（第 01 章 8 节的伪代码），三个目标的机制都挂在循环的不同位置——先通读循环骨架，再按兴趣深入分支。

**第二，警惕「目标混合体」模块**：调度器同时服务三个目标（延迟优先级、吞吐 batch、确定性的可重放），是最难读的模块。读它的正确姿势是带着本章的问题清单去：这里哪个分支在保延迟？哪个在保吞吐？哪个 if 是确定性的让步？——问题清单先于代码，是读复杂系统的不二法门。

DeepInfer 仓库里对应关系尤其清晰（目标单一的好处）：`server` 目录是引擎循环，`decode` 相关是 decode 节点逻辑，算子库按 FlashMLA/DeepGEMM/DeepEP 分仓。带着三目标地图进去，每个目录的自我介绍都能对上号。

## 一个数字的旅程：一条请求的 SLO 视角

把本章所有概念串成一条时间线。设一条典型请求：输入 2000 token（含 1500 token 共享 system prompt）、输出 600 token，SLO 是 P99 TTFT < 2 s、P99 ITL < 100 ms。跟着它走一遍：

**t = 0：到达。** 网关鉴权、计费，1~10 ms。排队论在后台运转：Little 定律决定此刻系统里有多少并发（第 01 章），调度器的队列里它前面排着几条请求。

**t = 5 ms：入队。** 调度器看它的「预算档案」：TTFT 截止时刻 = 到达 + 2 s。前 1500 token 的前缀在缓存里命中（第 06 章），剩余 500 token 需要 prefill——按 1.2 s/万 token 的速率约 60 ms 的计算量，budget 充裕，标黄（不急）。

**t = 30 ms：prefill 开始。** 假如此刻系统正忙，它可能要等当前 decode step 结束才能插进 batch（chunked 调度）。这段「等空位」的时间是 TTFT 的排队段——如果它等到 t = 1.5 s 才开始 prefill，TTFT 预算只剩 500 ms，调度器此刻要把它标红：优先安排甚至抢占别人的 chunk 槽。

**t = 200 ms：首 token 产出。** TTFT 定格在 200 ms，远好于 SLO。从这里开始它的每个 token 都进入 ITL 预算：600 个 token、每 100 ms 一个，最迟 t = 60 s 完成。

**t = 200 ms ~ 12 s：decode 巡航。** 它在 batch 里随进随出的邻居们一起跑。某一步它旁边来了条长 KV 请求，step 从 40 ms 涨到 70 ms——ITL 预算还够。另一步它自己被调度器看中用推测解码带了 3 个 token（第 08 章），这一步的「有效 ITL」摊薄到 15 ms——预算攒下了富余。

**t = 8 s：一次险情。** 显存吃紧，调度器考虑抢占名单。它是「预算富余 + 已生成 70%」的请求——按「已完成度+富余度」的评分，抢先被牺牲的应该是「预算赤字且刚开始」的别的请求……或者恰好是它自己（牺牲已沉没 70% 的请求最亏，调度器的评分会救它，但极端情况下还是它）。被抢占的话它的 KV 逐出到 3FS（第 06 章），排队等回归——ITL 预算瞬间爆掉，这次请求注定超 SLO，进 Goodput 的分母。

**t = 12 s：正常完成。** 600 token 全部吐完，流式帧走完最后一程。它的一生：2 个 SLO 指标全程在岗、4 个子系统（网关、调度器、缓存、算子）轮流服务、至少 3 次险情被机制化解——而这只是同批 64 条请求里的一条。

这个走查的目的：**SLO 不是两个数字，是一条贯穿请求生命周期的时间预算线，每个子系统都在为这条线打工**。后面每一章，都是把其中某一站放大到整章的篇幅。

把旅程里的分散量合成一张「预算卡」，你可以直接抄进自己的设计文档：

```text
用户体感总时延 T_total
  = TTFT + TPOT × (N_out - 1)        # N_out = 输出 token 数
  = [排队 + prefill' + 编译(可异步) + KV取回]    # TTFT 四段
  + [W/B + K] / 带宽 × N_out         # TPOT 的搬运公式（第 01/02 章）

其中：
  prefill' = prefill(未命中前缀部分)     # 前缀缓存跳过命中部分
  排队 ≈ f(到达率, 服务率, 调度策略)      # Little 定律管宏观
  KV取回 ≈ 命中块大小 / (网络带宽 × 并行度)

管理动作 → 作用点：
  加机器/扩容        → 排队↓（分母变大）
  前缀缓存           → prefill'↓
  chunked 调度       → 排队↓（decode 不被 prefill 堵）
  组批/MLA/推测解码  → TPOT↓
  3FS 预热策略       → KV取回↓
```

这张卡的价值在于**每个优化手段都挂在公式的某一项上**——评估任何「新优化」时，先问它改哪一项、改多少，公式会诚实地告诉你总时延怎么动。同样一张卡也能反推容量：给定 SLO 和流量，逐项求解需要多少资源。第 11 章的部署配方就是这张卡的工程化展开。

## 常见误解澄清

**误解一：「延迟低=吞吐低的零和游戏。」** 三个目标确实打架，但不是零和：第 06 章的前缀缓存同时改善 TTFT（命中跳过）和吞吐（省算力）——结构性优化常常是正和的。打架的通常是「参数级」权衡（batch 大小、chunk 尺寸），「结构性」优化（分页、压缩、复用）往往全家受益。先做结构性优化，再调参数。

**误解二：「确定性就是固定 seed。」** 本章拆过了：固定 seed 只管住 RNG 一个泄漏源，浮点归约顺序照样漏。而且即便两个都堵上，「同一请求跑两次结果一致」还要求调度路径确定（抢占发生的时机不影响数值路径）——确定性是一套工程，不是一个开关。

**误解三：「TTFT 优化就是优化 prefill 速度。」** TTFT 拆解成四段（排队、prefill、编译、KV 取回），生产里排队和取回经常是大头。只盯算子优化的团队，经常发现 TTFT 曲线纹丝不动——瓶颈在队列里，不在 GPU 里。

**误解四：「确定性会拖慢一切。」** 确定性的开销集中在归约和 RNG 两个点，且都有「隔离到请求粒度」的折中方案——生产实测的代价通常在个位数百分比。拿「确定性和性能不可兼得」当借口跳过它，是把几毫秒的效率看得比「能测试、能复现、能排障」重——后者在系统出事的那一天，价值以停机时长计。

**误解五：「压测并发数越高越好。」** 单点高并发数字是营销素材不是工程结论。要看的是负载扫描曲线上的 Goodput 峰值和崩溃点距离——「P99 达标下的最大稳定负载」才是一个系统的真实容量。拿崩溃区边缘的瞬时吞吐做容量规划，第一次线上突发就会教做人。

**误解六：「三个目标都做到了，服务就好了。」** 还差一层：目标之间有**汇率**。压 P99 牺牲多少吞吐、换确定性花几个百分点——这些交换比率本身是可管理的设计参数。成熟的团队把汇率显式化（「我们用 12% 吞吐换 P99 达标」）并定期复盘；不成熟的团队把汇率藏在调度器的魔数里，谁也说不清代价是什么。第 07 章你会看到 DeepInfer 把这些汇率写成了可以调的配置。

## 小结

**目标一（低延迟）**：其实是两个目标——TTFT（prefill 决定，计算受限，可拆四段：排队/prefill/编译/KV 取回）和 TPOT（decode 决定，带宽受限，公式 $\frac{W}{B}+K$）。两者优化手段无交集，混跑互相污染；解法是物理分离（P/D）或时间切碎（chunked prefill）。节奏方差和流式分片同样影响体感，SLO 要埋在客户端口径。

**目标二（高吞吐）**：引擎是组批摊销——单 token 成本 $\frac{W}{B}+K$，权重项随 batch 摊薄、KV 项是底价，所以 MLA 压 $K$、分页管理 $B$ 上限、3FS 扩容都是这张公式上的手术。前缀缓存把复用从同时刻并发扩展到时间轴全流量；推测解码吃剩余闲算力。吞吐数字必带三限定词（模型/分布/并发），科学口径是 Goodput。成本链从 $25/h 租金推到 $0.5~1/M token，每个优化都是链上的乘数。

**目标三（确定性）**：batch-invariance 是生产门槛。四个泄漏源（浮点归约顺序、全局 RNG、AllReduce 到达序、异步流水相位），全藏在「为效率而共享」的地方；拆法是隔离到请求粒度。换来的回归测试/A/B/重放能力是工程体系的基础设施，验证靠四个构造性测试（双跑/邻居注入/重放对齐/抢占路径）。

**共同底层**：三个目标的最强手段都压在 KV Cache 的四项能力上（索引、共享、逐出恢复、精确截断）——它是存储系统不是缓存。**仲裁机制是 SLO**：从产品形态倒推数字、编译成调度器优先级，Goodput 峰值定容量；P99 是拿平均值的钱买的，目标间汇率要显式管理。DeepInfer 的目标指纹：吞吐（成本）> P99 尾延迟 > 平均延迟 > 通用性。

下一章进入第一个「机制章」：E/P/D 分离的总体架构——目标一和目标二的冲突在那里被物理结构化解。

## 自测：开篇问题的参考答案

对照开篇的五个问题，检验自己的掌握度（答案都是本章的原话，能独立复述才算过）：

**Q1：TTFT 和 TPOT 分别由哪段计算决定？** TTFT 由 prefill 决定（计算受限，可拆四段：排队、prefill 计算、约束编译、KV 取回）；TPOT 由 decode 决定（带宽受限，公式是搬运量除以带宽）。两者瓶颈资源不同，所以优化手段几乎无交集——「低延迟」实际是两个目标。

**Q2：为什么大 batch 几乎总是划算的？** 单 token 摊销成本是 $\frac{W}{B}+K$：权重读取全批共享（摊薄项），KV 是每请求私有（底价项）。batch 从 1 到 64，成本降到 1/24 而 TPOT 只恶化不到 3 倍。两个前提：流量密度够拼（调度器的战场）、显存装得下并发 KV（分页存储的战场）。

**Q3：吞吐数字的三个水分维度？** 什么模型（参数量定搬运量）、什么长度分布（prefill/decode 占比差数倍）、什么并发（单请求延迟和满载吞吐是两个极端）。三限定词齐全的数字才可比；更科学的口径是 Goodput（SLO 达标吞吐）。

**Q4：确定性的两个泄漏源？** 浮点加法不满足结合律（批组成改变归约顺序 → 低位误差 → 数十层放大 → 输出分岔）；全局随机数流（邻居请求抽走随机数改变我的采样）。分布式再加两个：AllReduce 到达顺序、异步流水相位。拆法是隔离到请求粒度。

**Q5：三个目标为什么都压在 KV Cache 上？** TTFT 靠前缀命中（要索引共享）、吞吐靠 3FS 复用（要逐出恢复）、确定性靠重放对齐（要状态还原）、推测解码靠回滚（要精确截断）——四项能力都是存储系统级的能力，不是「缓存」级别的。

哪题答不顺，回对应章节的段落再读一遍——**能讲给别人听，才是真的懂了**。

## 思考题

1. 用本章的公式 $\frac{W}{B}+K$ 估算：若 MLA 把 $K$ 从 1 GB 压到 0.2 GB，$B=64$ 时单 token 摊销降多少？TPOT 从 30 ms 降到大约多少？再想想：为什么 $B=1$ 时 MLA 对 TPOT 几乎无改善（提示：$W$ 项主导）？
2. 一个 agent 平台流量：每条请求输入 2000 token（其中 1800 是共享的 system prompt + 工具说明）、输出 300 token。前缀缓存命中率 90% 时，prefill 计算省多少？如果系统 p95 TTFT 反而变差了，最可能坏在哪个环节（提示：TTFT 四段拆解里，「取回」那段）？
3. 你要在单机上同时服务「交互聊天」和「夜间批处理」两类流量。SLO 怎么定？调度器应该把批处理请求排在哪个 batch（白天/夜间/填缝）？推测解码对哪类流量更划算（提示：谁有更多闲算力）？
4. 设计验证 batch-invariance 的测试：随机生成 500 条请求，怎么安排它们的两轮运行，才能覆盖「批组成不同」这个变量？浮点归约的泄漏用什么样的请求组合最容易暴露（提示：长度差异大的请求拼批，padding 和归约顺序变化最多）？
5. 有人说「P99 TPOT 100 ms 的 SLO 太苛刻了，平均值 50 ms 就很好」。用第 01 章 2.5 的 agent 链例子反驳：50 次串行调用、每次 5% 尾部概率，链路级掉尾概率多少？链路的 p99 时延和单请求 p99 时延是什么关系？
6. 用成本解剖的推导链重算：如果前缀缓存把平均 prefill 计算省了 30%、负载不变，每百万 token 成本降多少？如果同时 MFU 从 50% 提到 60%（prefill 提速 20%）呢？两个优化叠加是乘法还是加法？
7. 压测设计题：你要为一个「输入 3000 token（80% 共享前缀）、输出 500 token」的 agent 流量画像做容量规划。压测请求怎么生成才能模拟前缀结构（提示：压测工具通常随机生成输入，前缀缓存命中率会是 0——怎么注入共享前缀）？如果不注入，测出的 TTFT/吞吐和生产比会偏差多少、偏哪个方向？
8. 长思考模型的思考链 KV「即焚」策略（生成完立刻释放）：它提高并发容量，但牺牲了什么能力（提示：第 06 章的 KV 复用对象里，哪些场景需要回看思考）？如果 10% 的请求会触发「继续思考」（接着上次的思考链继续），即焚策略怎么改？做一个收益/代价表。
9. MFU 解剖清单里五项损耗，各自对应的优化（FlashMLA、分组 GEMM、通信重叠、kernel 融合、对齐 padding）分别是什么工程量级（人日量级）？如果你只能投资其中一项，按「MFU 提升/工程成本」的性价比排序——你会发现答案取决于你的流量里长序列的占比，为什么？
